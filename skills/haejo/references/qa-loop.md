# 테스트 > 개선 반복 (QA 루프)

사용자가 "테스트 반복해줘", "테스트 > 개선 > 커밋"을 요청했을 때 읽는다([../SKILL.md](../SKILL.md) 6절). 절 번호는 SKILL.md의 절이다.

목표는 마일스톤 체크가 아니라 "하나의 완성된 프로젝트"다. 천천히 꼼꼼하게 한다. 사용자가 시간(예: 6시간)을 주면 그 안에서 반복한다. 시간이나 끝내는 기준이 말에 없으면 처음 질문에서 묻는다(SKILL.md 2절).

## 준비

1. 테스트케이스를 먼저 기획한다.
   - 기준: 페르소나·시나리오, 체크리스트의 ✅ 항목, 지난 회차에 고친 것.
   - 케이스마다 번호, 단계, 기대 결과를 적는다.
2. 한 번에 하나만 돌 수 있는 도구(예: 게임 엔진 배치 실행, 같은 포트의 개발 서버)가 있는지 프로젝트 규칙([projects.md](projects.md))에서 본다. 있으면 테스트와 개선을 겹치지 않게 차례로 돌린다.
3. 회차 기록 위치를 정한다. 프로젝트에 정해진 곳이 있으면 그곳, 없으면 저장소의 `qa-reports/round-NN.md`에 둔다.

## 테스트 회차

테스트는 **만든 눈과 다른 눈**으로 한다. 회차마다 `Agent` 하위 에이전트를 새로 띄워 맡긴다(SKILL.md 2절 기본값의 모델).

- 테스트 에이전트는 **코드를 고치지 않는다.** 케이스를 수행하고 보고서만 쓴다.
- 주는 것: 케이스 목록, 지난 회차에 고친 것 목록. **이전 보고서와 이 세션의 요약은 주지 않는다**(편향 방지).
- 테스터 관점으로 판단하게 한다: 잘된 것 / 고칠 것(버그, 막히는 흐름) / UI·UX·디자인 개선점.
- 컴퓨터 사용을 허락받았으면(SKILL.md 2절 기본값은 허락 안 함) 실제로 실행해 본다(예: 처음 10분, 주요 메뉴 흐름). 허락받지 않았으면 자동 테스트·스크린샷·브라우저 미리보기로 대신한다.
- 결과는 심각도별로 나눈다: 꼭 고칠 것 / 고치면 좋은 것 / 기획 결정 필요.
- 하위 에이전트를 쓸 수 없으면 이 세션이 직접 테스트하고, 그 사실을 보고에 적는다.

## 개선 회차

이 세션이 직접 고친다.

- 꼭 고칠 것 → 고치면 좋은 것 순서로 고친다.
- 기획 결정이 필요한 것은 비슷한 제품을 조사해 이 프로젝트에 맞는 쪽으로 정하고, 체크리스트에 기록한다. 사용자 취향인 결정은 정하지 않고 모아 둔다([decisions.md](decisions.md) "사용자 취향인 결정").
- 남는 시간에는 체크리스트의 남은 항목을 개발한다. 확인이 필요하거나 어려운 것은 후순위로 둔다.
- 확인은 프로젝트 규칙을 따른다. 정해진 게 없으면 [test.md](test.md) "돌릴 테스트"대로 그 고침에 닿는 테스트만 돌리고, 전체 테스트는 루프를 멈출 때 한 번 돌린다.
- git은 처음 질문에서 받은 범위만큼만 한다(SKILL.md 2절). "커밋까지" 이상을 받았으면 회차마다 목적별로 커밋하고 지난 회차 보고서 파일도 함께 담는다([git.md](git.md)). 받지 않았으면 파일만 고친다.

## 다음 회차

- 고친 뒤 새 테스트 에이전트로 다음 회차를 돌린다. 회귀 케이스(지난 회차에 고친 것)는 매 회차 넣는다.
- "PR까지"를 받았으면 PR 하나에 회차마다 커밋을 더하고 본문을 갱신한다. 머지는 "머지까지"를 받았거나 사용자가 시킬 때만 한다.
- 회차 제목 예: "QA 9회차: 이웃에게 선물·편지 + 회귀"

## 멈추는 때

- 처음 질문에서 정한 시간이 다 됐거나 끝내는 기준을 채웠을 때
- 두 회차 연속 꼭 고칠 것이 없고, 남은 체크리스트 항목이 모두 확인 필요·어려움·사용자 항목일 때
- 결제나 되돌리기 어려운 결정이 필요할 때 → 그것만 사용자에게 남기고, 나머지는 계속한다

## 마지막 보고

- 회차 수, 고친 것 수, 바뀐 파일(커밋·PR을 했으면 그 링크)
- 아직 남은 문제
- 사용자가 직접 볼 것(휴대폰으로 읽기 좋게)
