# 커밋·PR·머지

처음 질문에서 "커밋까지" 이상을 받았거나 사용자가 "커밋해줘", "PR 만들어줘", "머지해줘"라고 했을 때만 읽는다. 무엇을 어디까지 하는지는 [../SKILL.md](../SKILL.md) 2절이 원본이고, 여기는 하게 됐을 때의 방법이다. 절 번호는 SKILL.md의 절이다.

## 범위마다 하는 일

| 받은 범위 | 하는 일 |
|---|---|
| 커밋까지 | 지금 브랜치에 목적별로 커밋한다. 기본 브랜치에 직접 커밋하게 되면 먼저 한 줄로 알린다. push는 하지 않는다. |
| PR까지 | 기본 브랜치에서 새 브랜치를 만들어 커밋·push하고, `gh pr create`로 기본 브랜치 대상 PR을 만든다. 머지는 하지 않고 PR 링크를 알린다. |
| 머지까지 | PR을 만든 뒤 SKILL.md 6절 확인과 CI를 통과하면 squash로 머지한다. |

- **한 일 = 브랜치 하나 = PR 하나.** 추가 고침(검토 지적, CI 실패)은 같은 PR에 커밋을 더하고 본문을 갱신한다.
- `gh`가 없거나 인증이 안 되면 브랜치 push까지 하고 그 사실을 알린다.
- GitHub 원격이 없거나 git이 아닌 프로젝트는 PR 없이 커밋까지만 한다.
- 받은 범위 밖의 일은 하지 않는다. 태그는 사용자가 달아 달라고 할 때만 단다(꼴은 [rules.md](rules.md) "태그").

## 커밋 메시지 꼴

모든 커밋(일하는 커밋, squash 커밋)에 쓴다. 프로젝트 CLAUDE.md에 커밋 형식이 따로 있으면 그것을 따른다.

- 제목 = `<타입>: <결과 한 줄>`. 타입은 영어(Conventional Commits), 내용은 사용자의 언어로 "무엇이 됐나"를 쓴다. 50자 안팎, 끝에 마침표 없음.
- 타입: `feat`(새 기능) · `fix`(버그 고침) · `docs`(문서·README) · `style`(화면 꾸밈·서식, 동작 같음) · `refactor`(동작 같은 코드 정리) · `test`(테스트) · `perf`(빠르게) · `build`(설치·빌드·의존성) · `ci`(CI 설정) · `chore`(그 밖의 잡일). 여러 개에 걸치면 가장 큰 결과의 타입 하나.
- 본문 = 결과 핵심만 `- `로 1~6줄. 과정·시행착오는 적지 않는다. 작은 커밋은 본문을 생략해도 된다. 커밋 꼬리표는 SKILL.md 2절 기본값("내 방식"의 값, 없으면 `Co-Authored-By` 남기기)대로 맨 끝에.
- 한 커밋 = 목적 하나. 목적이 다르면 커밋을 나눈다.
- 커밋 전에 `git diff --cached`에서 비밀값처럼 보이는 문자열을 찾는다([external-setup.md](external-setup.md) "비밀값").

## PR 본문 꼴

PR 본문은 최종 요약이다. 커밋을 더할 때마다 갱신한다. PR 제목도 `<타입>: <결과>`로 쓴다.

```
## 무엇을 바꿨나
- <체크리스트 번호나 시안 항목> <한 줄>
## 어떻게 확인했나
- `<명령>` → 종료 코드 0, <결과 줄 그대로, 예: 12 passed>
- 시안 대조: A1 됐음 · A2 됐음
- 돌리지 않은 범위: <예: 전체 테스트는 마일스톤 끝에>
## 범위 밖에서 건드린 것
- 없음
## 확인 못 한 것·남은 것
- …
## 나중에
- <사소한 검토 지적, 없으면 칸째 뺀다>
```

## 머지

- **Squash and merge로 한다.** PR 하나가 기본 브랜치에 커밋 하나로 남는다(`gh pr merge <번호> --squash --subject "<제목>" --body "<본문>" --delete-branch`). 제목·본문은 위 커밋 메시지 꼴, 제목 끝에 PR 번호. 중간 커밋은 나열하지 않고 PR 전체의 결과만 쓴다.
- 머지 전에 본다: PR 본문 네 칸이 찼나 · CI가 모두 통과했나 · 바뀐 파일이 범위 안인가 · 기본 브랜치와 충돌이 없나 · 위험한 변경이면 검토를 했나([test.md](test.md) "위험한 변경 검토").
- "PR까지"만 받았으면 머지하지 않는다. 확인 결과를 아래 꼴로 알리고 멈춘다. 머지는 사용자가 시킬 때 한다.
  ```
  **무엇**: <PR 링크> — <한 줄>
  **확인**: 요약(4칸) · 테스트(CI / 직접 돌림) · 범위(파일 3개, 범위 밖 없음) · 충돌 없음 · 검토: 안 함(위험 아님) / 함 — 결과 한 줄
  **확인 못 한 것·남은 것**: <PR 본문 그 칸 그대로>
  **머지하면**: 배포 여부 · 따로 할 설치·반영(예: `./install.sh`)
  ```
- PR이 여럿이면 하나씩 머지한다. 먼저 머지된 것과 충돌하면 기본 브랜치를 받아 고친 뒤 머지한다.
- **main push가 곧 배포인 프로젝트**: 머지가 배포다. "머지까지"를 받았어도 머지 직전에 한 번 확인받는다. 자리 비움 중이면 머지하지 않고 "돌아오시면 정할 것"에 둔다.
- 머지할 때 저장소 조건을 건너뛰는 옵션(`--admin`)은 사용자가 말하지 않으면 쓰지 않는다.
- 머지한 뒤 그 브랜치와 작업 폴더(worktree)는 지운다(원격 브랜치는 `--delete-branch`). 하위 세션이 한 일이면 그 세션은 보관한다("내 방식"에서 바꾼다. 삭제는 사용자가 정해 뒀을 때만).

## CI 시간

비공개 저장소는 Actions 시간이 한도·돈이다.

- CI를 만들거나 고칠 때는 테스트에 닿는 파일이 바뀔 때만 돌게 하고(`paths`), 같은 PR의 앞 실행은 끊는다(`concurrency`). 문서만 바뀐 PR에는 돌지 않게 한다. 시험에 닿는 경로를 빠뜨리지 않는다.
- CI가 몇 초 만에 실패하면 시험 실패로 보지 말고 잡이 시작됐는지부터 본다.
- 한도나 결제로 잡이 시작되지 않으면 사용자에게 알리고 로컬 시험으로 이어 갈지 묻는다. 결제는 사용자 몫이다. 이어 가면 CI와 같은 명령을 직접 돌려 종료 코드와 결과 줄을 보고 머지한다.
