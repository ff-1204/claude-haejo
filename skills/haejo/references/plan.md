# 기획 플로우

기획 요청(처음부터 기획, 페르소나 더하기, 점수·우선순위 다시 보기, 마일스톤 끝 표시, 로드맵 상태 보기)이 왔을 때, 로드맵대로 개발할 줄을 고를 때 읽는다([../SKILL.md](../SKILL.md) 3절, SKILL.md 5절). 절 번호 가운데 "SKILL.md N절"은 SKILL.md의 절이고, 맨 "N절"은 매핑 문서(`persona-checklist-map.md`)의 절이다.

플로우를 고르고, 단계마다 단계 문서(`references/<단계>.md`)를 읽어 그대로 하고, 확인 지점에서 묻고, 마지막에 보고한다. 먼저 [rules.md](rules.md)를 읽는다. 문서 이름, 머리 줄, 번호, 묻는 법이 거기 있다.

## 지금 상태 보기

먼저 기획마다 `node ~/.claude/skills/haejo/scripts/status.js <personas.md가 있는 폴더>`를 돌린다(한 주제면 `--prefix <절>`, 체크리스트를 못 찾으면 `--checklist <파일>`). 아래 2~4의 시각 비교와 수 세기, 그리고 내용 검사(장면 없는 페르소나, 번호·표시 없는 단계와 체크리스트에 없는 번호, score.js로 다시 센 점수와 매핑 1절 표, 순서에 빠진 묶음, 로드맵에 빠진 묶음)를 스크립트가 한다. 결과 표의 "이어 할 곳"이 처음 낡은 단계이고, "왜" 칸(`내용: …` / `시각: …`)을 읽고 거기서부터 이어 한다. "낡음(시각만)"은 내용은 맞고 시각 줄만 늦은 것이다. "내용 검사 못 함(…)"은 꼴이 달라 못 본 것이라 시각으로만 판단한 것이다(`--no-content`로 내용 검사를 끈다). 눈으로 다시 세지 않는다. 스크립트를 쓸 수 없을 때(Node 없음)만 아래대로 직접 본다. status.js를 고쳤으면 `node ~/.claude/skills/haejo/tests/run.js`로 시험한다.

상태 칸에 `손으로 고침?(갱신 줄보다 뒤에 바뀜: …)`이 붙으면, 그 문서가 가장 늦은 `> 갱신:`보다 60분 넘게 뒤에 바뀐 것이다(git 커밋 시각, 커밋 안 됐으면 파일 수정 시각). 경고만 붙고 "이어 할 곳"은 그대로라, 사용자에게 손으로 고친 내용을 반영할지 묻는다. git 밖이면 검사하지 않고, `--no-git`으로 끌 수 있다.

1. `personas.md`의 `> 문서:` 줄로 문서 위치를 찾는다. 없으면 기본 위치(rules.md)를 쓴다. `**/personas.md`가 여럿이면 기획(제품 전체 + 주제마다)이 여럿이다. 아래 2~4를 **기획마다 따로** 보고, 상태 보고도 기획마다 한 덩어리로 낸다.
2. 문서 다섯 개가 있는지, 각 문서의 `> 갱신:` 날짜·시각을 본다.
3. **낡음** 판단 (앞 단계가 뒤 단계보다 늦게 갱신됐으면 뒤 단계가 낡음):
   - personas → scenarios → map(매핑 문서 머리 `> 갱신:`) → score(매핑 1절 아래 `> 점수:`) → priority(매핑 3절 아래 `> 순서:`). 예전 꼴이라 `> 점수:`·`> 순서:` 줄이 없으면 매핑 머리 `> 갱신:`을 쓰고, 다음 실행 때 그 줄을 만든다.
   - `roadmap.md`는 **그 기획의 순서 줄(제품이면 `I00-00`, 한 주제면 `<절>-00`)의 날짜·시각이 `roadmap.md` 갱신보다 늦을 때만** 낡음이다. 순서를 바꾸지 않은 점수·우선순위 실행은 로드맵을 낡게 만들지 않는다.
   - 시각이 최신이어도 내용이 어긋나면 낡음이다: 시나리오에 장면 없는 페르소나, 매핑에서 번호·표시 없는 단계나 체크리스트에 없는 번호, 매핑 1절 점수가 `score.js`를 다시 돌린 값과 다름, 매핑 1절 묶음이 3절 순서에 없음, 순서의 묶음(✅·⏸ 빼고)이 `roadmap.md` 세부 항목에 없음. 꼴이 달라 판단할 수 없으면 시각으로만 본다.
4. 진행 상태: 마일스톤마다 세부 항목 ✅ 수 / 전체, 시나리오 ✅·🔜·일부만(한 줄에 둘 다 있는 단계, 따로 셈)·❌ 수.

"로드맵 어디까지 왔어?"처럼 상태만 물었으면 이 결과와 다음 세부 항목을 알리고 끝낸다. 아무것도 고치지 않는다.

## 플로우 고르기

| 사용자 말 (예) | 플로우 | 단계 순서 (모드) |
|---|---|---|
| "처음부터 기획해줘", "페르소나부터 로드맵까지", "<주제>를 기획하고 개선해줘" | 전체 | core(새로) → personas(새로) → scenarios(새로) → map(전체) → score → priority(새로) → milestones(새로). 기획 크기(전체 / 한 주제)는 처음 질문에서 정한다(rules.md "기획 크기") |
| "페르소나 하나 더 추가해줘: <누구>", "이런 사용자도 넣어줘" | 더하기 | personas(더하기) → scenarios(더하기) → map(더해진 것만) → score → priority(바뀐 곳만) → milestones(바뀐 곳만) |
| "점수 다시 계산해줘", "우선순위 다시 봐줘" | 다시 보기 | score → priority(바뀐 곳만) → (순서가 바뀌었으면) milestones(바뀐 곳만) |
| "M2 끝났어", "시나리오 갱신해줘" | 갱신 | milestones(끝 표시) → scenarios(갱신) → score → priority(바뀐 곳만) → (순서가 바뀌었으면) milestones(바뀐 곳만) |
| "핵심 경험을 바꾸고 싶어" | 바탕 바꾸기 | core(바꾸기) → personas(다시 매김) → scenarios(갱신) → map(전체) → score → priority(바뀐 곳만) → milestones(바뀐 곳만) |
| "로드맵대로 개발해줘", "M2 진행해줘" | 개발 | 아래 "개발 플로우" |
| "시나리오만 다시 써줘", "어떤 기능이 제일 많이 필요해?" | 한 단계만 | 말한 단계 하나(점수만 궁금하면 score). rules.md "한 단계만 돌릴 때" |

- "전체"를 골랐는데 문서가 이미 있으면 처음부터 다시 쓰지 않는다. **낡은 단계부터** 이어 한다(한 주제를 고르면 이 줄 대신 새 주제 폴더에 처음부터). 처음부터 다시 쓰는 건 사용자가 그렇게 말했을 때만.
- 말이 애매하면 상태를 보고 가장 가까운 플로우를 고른다. 그래도 둘 이상이면 처음 질문에 플로우 선택을 넣는다.

## 묻는 지점

모두 선택 UI로 묻는다(rules.md "묻기").

| 언제 | 무엇을 | 추천 |
|---|---|---|
| 처음 질문 (전체·바탕 바꾸기만, SKILL.md 2절 화면에 함께) | 기획 크기(전체 / 한 주제), 문서 위치(**공개 저장소일 때만**: "저장소 안 = 공개" / "저장소 밖", rules.md "공개 저장소") | 이미 돌아가는 프로젝트에 주제가 있으면 한 주제, 아니면 전체 |
| core 끝 | 핵심 경험 목록과 범위가 맞는지 (**항상 묻는다**, 아래) | 제안한 그대로 |
| milestones 끝 | 마일스톤 수·경계, 사람 테스트 자리, 태그 번호 | 제안한 그대로 |
| 끝 | 바로 개발로 갈지 | 다음 세부 항목부터 |

**묻지 않고 Claude가 정하는 것** (보고의 "정한 것"에 적는다. 사용자가 말로 바꾸면 그대로 따른다):
- 진행 방식: 위 확인 지점마다 멈춤. 사용자가 "알아서 끝까지"나 "단계마다 멈춰"라고 하면 그대로.
- 페르소나 수: 5명. 사용자가 수를 말하면 그대로.
- 문서 위치(비공개 저장소): 한 주제면 `docs/기획/<절>-<이름>/`, 전체면 저장소 루트.
- 미루기 규칙(어려운 것·사람 확인 필요는 뒤로)과 난이도 기준: 둘 다 쓰고 기본 기준. 보고에 "미룬 것"을 짧게 보인다.

규칙:
- 처음 질문에 이미 답이 있는 것(사용자 말, 메모리, 문서 머리)은 빼고 묻는다.
- **기획 문서도 파일만 고친다.** 기획만 하는 요청에는 git 범위를 묻지 않고, 커밋은 사용자가 시킬 때만 한다(SKILL.md 2절).
- **핵심 경험은 "알아서 끝까지"여도 확인받는다.** 여기가 틀리면 뒤 기획이 모두 헛돈다. 사용자가 자리를 비워 물을 수 없으면 추천대로 이어 가되, 마지막 보고 맨 위에 "확인해 주세요: 핵심 경험"을 두고 바뀌면 바탕 바꾸기 플로우로 다시 돈다고 적는다.
- "알아서 끝까지"면 milestones 끝과 마지막 질문은 하지 않는다. 추천대로 정하고, 개발은 시작하지 않는다(보고의 다음 할 일 1번으로 둔다). 마지막 보고에 "추천대로 정한 것" 목록을 붙인다.
- 사용자가 자리를 비웠으면([wrap-up.md](wrap-up.md) "자리 비움") 기획 크기·문서 위치도 추천대로 정하고 보고에 적는다.
- "단계마다 멈춤"이면 단계 하나가 끝날 때마다 한 줄 보고 후 계속할지 묻는다.
- 더하기·다시 보기·갱신 플로우는 처음 질문 없이 바로 돈다. 순서가 바뀌면 보고에 "바뀐 자리"를 보이고, 묻지는 않는다.

## 단계 문서 읽기

- 플로우 표의 단계마다 단계 문서를 읽고 적힌 모드대로 한다: [core](core.md) · [personas](personas.md) · [scenarios](scenarios.md) · [map](map.md) · [score](score.md) · [priority](priority.md) · [milestones](milestones.md). 예: 더하기 플로우의 personas 단계는 `personas.md`의 "더하기" 모드로, 누구를 더할지는 사용자 말 그대로.
- 단계가 끝나면 그 문서의 한 줄 보고를 사용자에게 그대로 전한다.
- 단계 문서가 "입력 문서가 없다"며 멈추라고 하면 그 앞 단계를 먼저 한다.
- 시나리오를 30명 넘게 새로 쓸 때는 서브에이전트로 나눠 쓴다(`scenarios.md` "30명이 넘을 때").
- 템플릿은 `assets/`, 점수 스크립트는 `scripts/score.js`에 있다.

## 개발 플로우

"로드맵대로 개발해줘", "M2 진행해줘"일 때 할 줄을 고르는 법이다. 구현·테스트·git은 SKILL.md 5~7절을 따른다.

1. **대상 마일스톤**: 사용자가 말한 것. 없으면 **✅가 아닌 세부 항목이 남은 첫 마일스톤**. 기획이 여럿이면 사용자가 고른 기획, 말하지 않았으면 **가장 최근에 만든 기획**(`personas.md` 첫 `> 갱신:`)을 쓰고 보고 첫 줄에 어느 기획인지 적는다. "M1"이 두 기획에 다 있고 하나가 이미 ✅면 아닌 쪽이다.
2. **세부 항목 고르기**: 그 마일스톤에서 ✅가 아닌 줄. `(사용자)` 표시가 있는 줄과 사람 테스트(`T1` 등)는 하지 않고 보고의 "사용자 몫"에 모은다.
3. **줄마다 기준 세우기**: 그 줄의 체크리스트 번호와 "끝났다고 보는 것"이 기준이다(시안 구실을 한다). 그 번호를 가진 시나리오 단계들(누구의 몇 번 단계인지와 문장)을 여정으로 먼저 적는다. 화면·문구가 걸린 줄은 그림 시안을 먼저 거친다([mockup.md](mockup.md)).
4. **줄을 차례로 한다**: 이 세션이 직접 구현하고 테스트한다. 끝난 줄은 `roadmap.md`와 체크리스트에 ✅를 표시하고, 줄마다 바뀐 파일을 적어 둔다. 하위 세션은 처음 질문에서 맡기라고 했을 때만 쓴다([sessions.md](sessions.md)).
5. **마일스톤 끝**: 세부 항목이 모두 ✅면
   - 전체 검증을 한 번 한다(프로젝트 규칙의 전체 테스트, 여정 테스트). 줄마다는 관련 테스트만 돌렸으니 여기가 전체 테스트 자리다([wrap-up.md](wrap-up.md) "마무리"). 테스트 반복([qa-loop.md](qa-loop.md))이 돌고 있으면 그 회차로 대신한다.
   - 갱신 플로우를 돈다(milestones 끝 표시 → scenarios 갱신 → score → priority).
   - 태그는 사용자가 달아 달라고 할 때만 단다(꼴은 rules.md "태그").
   - 다음 마일스톤으로 넘어갈지는 '개발 범위'(SKILL.md 2절 기본값은 이 마일스톤만)를 따른다.

## 보고

- 단계마다 한 줄 보고를 이어 붙인다.
- 끝에:
  - 만든·바뀐 문서 (링크)
  - 🔜 상위 5개 묶음과 점수
  - 마일스톤 표 (이름 · 끝 기준 페르소나 · 세부 항목 ✅/전체)
  - 정한 것 / 추천대로 정한 것
  - 사용자 몫 (사람 테스트, `(사용자)` 줄)
  - 다음 할 일: 번호 붙은 선택지, 추천은 1번
- 문서를 고친 뒤 커밋은 하지 않는다. 사용자가 시키면 그때 한다(SKILL.md 2절).
