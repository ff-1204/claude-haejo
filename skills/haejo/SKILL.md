# haejo — 한마디로 끝까지

요청 → 기획 → 시안 검토 → 검토 완료 → 개발 진행 → 테스트 → 배포·머지. 사용자의 말을 읽고 **맞는 자리부터** 시작해 끝까지 간다. 일은 이 세션(메인)이 직접 한다.

## 0. 원칙과 "내 방식"

- 과정은 Claude가 정하고, 사용자가 정하는 곳은 처음 질문(2절), 시안 확인(4절), 핵심 경험 같은 취향 결정(3절·5절)이다. 그 밖에 멈춰서 묻는 것은 되돌리기 어려운 일뿐이다(배포가 되는 머지 직전, 결제·계정).
- 답과 보고는 결과부터 쓰는 쉬운 구어체로, 휴대폰에서 읽기 좋게 짧게 쓴다. 선택지는 번호를 붙인다.
- 문서 이름, 번호, 표시, 묻는 법 같은 공통 규칙은 [references/rules.md](references/rules.md)에 있다. 기획 문서를 다루기 전에 읽는다.
- **기본값과 "내 방식".** 이 스킬의 보고 꼴·알림·디자인 방식·시험 되풀이 횟수는 무난한 기본값이다. 사용자가 `references/projects.local.md`의 "내 방식" 절(이 PC에만 있는 파일, [references/projects.md](references/projects.md) 템플릿)에 다르게 적었으면 그쪽을 따른다. 사용자가 말로 방식을 바꾸면 그 절에 적어 두고 다음 세션부터도 쓴다. 단 git 범위(2절)는 "내 방식"으로 미리 정할 수 없다.
- **새 버전 안내.** 스킬을 시작할 때 `node ~/.claude/skills/haejo/scripts/check-update.js`를 한 번 돌린다. 한 줄이 나오면 마무리 보고 끝에 그대로 붙이고, 아무것도 안 나오면 아무 말도 하지 않는다. 스스로 업데이트하지 않는다. "내 방식"에 `새 버전 안내: 끔`이면 돌리지 않는다. check-update.js를 고쳤으면 `node ~/.claude/skills/haejo/tests/check-update.js`로 시험한다.

## 1. 요청 읽기

말을 읽고 시작할 자리를 정한다. 정한 자리는 첫 줄에 알린다(예: "시안 검토부터 할게요"). 앞 단계는 건너뛴다.

| 사용자 말 (예) | 시작 자리 | 건너뛰는 것 |
|---|---|---|
| "처음부터 기획해줘", "페르소나 하나 더", "점수 다시 계산해줘", "M2 끝났어" | 기획 (3절) | 없음. 기획만 하고 멈춘다 |
| "이 기능 넣어줘", "화면 바꿔줘", "시안 보여줘" | 시안 검토 (4절) | 기획 |
| "로드맵대로 개발해줘", "M2 진행해줘" | 개발 진행 (5절) | 기획. 세부 항목이 시안 구실을 한다(4절) |
| "이 버그 고쳐줘", 한두 파일의 작은 고침 | 개발 진행 (5절) | 기획·시안(4절의 건너뛰는 일) |
| "테스트 돌려줘", "테스트 반복해줘" | 테스트 (6절) | 앞 단계 전부 |
| "커밋해줘", "PR 만들어줘", "머지해줘", "배포해줘", "태그 달아줘" | 배포·머지 (7절) | 앞 단계 전부 |
| "로드맵 어디까지 왔어?", "진행중이니?" | 어느 단계도 아님 | 상태만 알린다. 아무것도 고치지 않는다(8절) |

- 자리를 정할 수 없을 때만 처음 질문(2절)에 "어디부터 할까요?"를 넣는다. 그 밖에는 묻지 않고 정한 자리를 알리기만 한다.
- 뒤 단계에서 걸리면 앞으로 돌아간다: 테스트에서 걸리면 개발로, 시안 자체가 틀렸으면 시안 검토로. 돌아간 이유를 한 줄로 알린다.

## 2. 처음 질문 (한 화면에 한 번)

요청을 읽은 뒤 **이번 일이 어디까지 갈지 미리 보고, 필요한 것만 한 화면에 묻는다.** 글로 묻지 않고 `AskUserQuestion`(선택 버튼 UI)으로 묻는다. 추천을 첫 번째 선택지에 두고 라벨 끝에 "(추천)"을 붙인다. 물을 것이 하나도 없으면 화면을 띄우지 않는다.

| 질문 | 언제 넣나 | 선택지 |
|---|---|---|
| git 범위 | 파일을 고치는 일일 때(개발 진행을 지나는 요청) | 파일만 고침(추천) / 커밋까지 / PR까지 / 머지까지 |
| 하위 세션 | 한 대화에 다 들어가지 않을 큰 일일 때(마일스톤 하나, 파일 수십 개) | 이 세션이 직접(추천) / 하위 세션에 맡기기 |
| 시간·끝내는 기준 | 테스트 반복처럼 끝이 정해지지 않은 일인데 말에 없을 때 | 예: 3시간 / 6시간 / 체크리스트 남은 항목 끝까지 |
| 기획 크기·문서 위치·시안 범위 | 전체 기획이나 바탕 바꾸기를 시작할 때([references/plan.md](references/plan.md) "묻는 지점") | 전체 / 한 주제, 공개 저장소면 문서 위치, 먼저 만들 것만 시안(추천) / 전부 시안으로 확정한 뒤 개발 |
| 더 정해 둘 것 | 위 질문이 하나라도 있을 때 맨 끝에 | 없음, 바로 시작(추천) / 자리를 비울 거예요 |

**git은 받은 만큼만 한다.** 이 규칙의 원본은 여기다(루트 CLAUDE.md와 다른 참조 문서는 여기를 가리킨다).

| 경우 | 규칙 |
|---|---|
| 기본 | 묻지 않았거나 "파일만 고침"이면 브랜치·커밋·push·PR·머지를 하지 않는다. 파일만 고치고, 바뀐 파일을 알리고 멈춘다. |
| 받은 범위 | "커밋까지"는 커밋, "PR까지"는 브랜치·커밋·push·PR, "머지까지"는 확인(6절)을 통과한 뒤 머지까지다. 범위 밖은 하지 않는다. |
| 말이 곧 허락 | 사용자가 "커밋해줘", "PR 만들어줘", "머지해줘"라고 하면 묻지 않고 말한 만큼만 한다. "커밋만", "아직 푸시하지 마"도 그대로 따른다. |
| 같은 세션 안 | 받은 답을 끝까지 쓰고 다시 묻지 않는다. 다른 저장소의 일은 다시 묻는다. |
| 대신 못 하는 것 | 메모리, 다른 세션의 답, "결재 빼고 알아서", "내 방식"은 git 범위를 대신하지 못한다. |
| 브리프로 시작한 세션 | 이 세션이 쓴 브리프로 시작한 하위 세션과 넘겨받은 새 세션은 브리프에 적힌 git 범위를 사용자 답으로 따르고 다시 묻지 않는다. 그래서 브리프에는 받은 범위를 빠짐없이 적는다. 브리프에 없는 git 작업은 하지 않는다. |
| 받지 않은 권한이 필요해지면 | 하지 않는다. 마무리 보고에 "이건 말씀하시면 해요"로 남긴다. 중간에 화면을 다시 띄우지 않는다. |
| 태그 | 사용자가 달아 달라고 할 때만 단다. 질문에 넣지 않고, 먼저 달거나 권하지 않는다. |
| git 저장소가 아닌 폴더 | 저장소를 스스로 만들지 않는다. 자리를 비우기 전 "되돌릴 지점"을 받았을 때만 `git init`과 이 PC에만 남는 커밋을 한다([references/wrap-up.md](references/wrap-up.md) "자리 비움"). |
| 읽기만 하는 git | `git status`·`git diff`·`git log`처럼 아무것도 바꾸지 않는 명령은 확인에 그대로 쓴다. |

**"더 정해 둘 것"의 답.** "없음"이면 바로 시작한다. 사용자가 직접 적은 말은 요청에 더해 시작 자리를 다시 정하고, 권한이 더 필요해질 때만 한 번 더 묻는다. "자리를 비울 거예요"면 8절 자리 비움으로 간다.

**묻지 않고 쓰는 기본값.** 사용자가 말했거나 메모리·"내 방식"에 적혀 있으면 그 값을 쓰고, 없으면 아래다. 쓴 값은 시작 보고에 "기본값으로 정한 것" 한 줄로 보인다.

| 항목 | 기본값 |
|---|---|
| 커밋 꼬리표 (커밋할 때만) | `Co-Authored-By` 남기기 |
| 검토 에이전트·하위 세션 모델 | 지금 세션과 같은 모델 |
| 알아서 할 범위 | 결재 빼고 알아서(5절) |
| 개발 범위 | 이 마일스톤만 |
| 컴퓨터 사용 (실제 실행해 보는 테스트) | 허락 안 함(자동 테스트·스크린샷만) |

**묻지 않을 때.** 사용자가 자리를 비웠거나 자동 이벤트로 시작된 턴이면 묻지 않고 이전 답을 쓴다. 이전 답이 없으면 git은 하지 않고 그 질문을 보고에 남긴다.

## 3. 기획

기획 요청이면 [references/plan.md](references/plan.md)를 읽고 따른다. 거기에 지금 상태 보기(`node ~/.claude/skills/haejo/scripts/status.js <personas.md가 있는 폴더>`), 플로우 고르기, 묻는 지점, 단계 문서 읽기, 보고가 있다.

- 단계는 research(조사와 기본 요소) → core(핵심 경험) → personas → scenarios → map → score → priority → systems(규칙 시안) → milestones다. 문서가 이미 있으면 낡은 단계부터 이어 한다. 기획 요청 가운데 research와 systems는 처음부터 기획할 때와 핵심 경험을 바꿀 때만 돈다.
- **핵심 경험과 규칙 시안은 "알아서 끝까지"여도 확인받는다.** 여기가 틀리면 뒤 기획이 모두 헛돈다. 기본 요소 목록(넣을 것 / 뺄 것)은 핵심 경험과 함께 확인받는다.
- 점수와 상태는 눈으로 세지 않고 스크립트(`scripts/score.js`, `scripts/status.js`)로 센다.
- 기획이 끝나면 개발을 스스로 시작하지 않는다. 보고의 다음 할 일 1번으로 둔다. 화면 틀 시안이 필요하면 그것이 1번이고 개발은 2번이다([references/mockup.md](references/mockup.md) "화면 틀 시안").

## 4. 시안 검토와 검토 완료

**시안은 그림이다.** 사용자가 보거나 정하는 결과가 있는 일(새 기능, 화면·문구·흐름, 제품 안의 규칙·시스템, 제품에 담기는 내용물, 문서 구조·규칙, 여러 단계에 걸친 일)은 만들기 전에 시안을 그림으로 보이고, "이대로"라고 할 때까지 고친다. 화면·사이트 시안은 Claude 아티팩트 페이지로 게시해 링크로 보이고, 흐름·구조는 그림으로 그린다. 표와 글은 그림에 담지 못한 것만 짧게 붙인다. 시안을 만들 때 [references/mockup.md](references/mockup.md)를 읽는다.

- **보이는 것은 디자인 스킬을 먼저 부른다.** 화면·아이콘·소개 페이지처럼 보이는 것을 만들거나 그 시안을 그릴 때는, 쓸 수 있는 디자인 스킬(예: 화면 디자인, 디자인 검토, 접근성 검토 스킬) 가운데 맞는 것을 먼저 불러 그 안내대로 한다. 하나도 없으면 보고에 그 사실을 적는다. 문구 한 줄이나 표시 조건처럼 모양이 바뀌지 않는 작은 고침에는 부르지 않는다.
- **그리기 전에**: 사용자가 참고할 제품을 말했거나 "조사해서"라고 했으면 그 기능을 먼저 조사하고, 이미 만든 기능이 있는 프로젝트면 지금 있는 것과 겹치는지 먼저 본다(mockup.md "그리기 전에").
- **올린 뒤에**: 화면 시안은 직접 열어 본 뒤에 보인다(mockup.md "시안은 그림이다").
- **화면 시안에 꼭 넣는 것**: 그 화면에 나오는 이름(탭, 단추, 이름표)의 표와, 처음 열었을 때·아직 못 쓰는 것의 모습이다(mockup.md "화면에 나오는 말", "아직 없을 때의 모습").
- 확정 전에는 구현을 시작하지 않는다. 확정된 시안이 개발과 테스트의 기준이다.
- 시안을 건너뛰는 일: 버그 고침처럼 바른 결과가 하나뿐인 일, 한두 파일의 작은 고침(도구 호출 열 번 안쪽. 화면·흐름이 크게 바뀌거나 저장 형식·경제 규칙을 건드리면 작은 고침이 아니다. 사용자가 보는 문구를 새로 정해야 하면 그 문장만 선택 UI로 확인받는다. 이름만 새로 생기면 묻지 않고 mockup.md "화면에 나오는 말"대로 짓는다), 사용자가 "시안 없이"라고 한 일, 로드맵 세부 항목(그 줄의 "끝났다고 보는 것"이 시안 구실을 한다. 화면·문구가 걸린 줄만 시안을 거치고, 첫 화면을 만들기 전에는 화면 틀 시안을 거친다).
- 사용자 취향인 결정(화면 문구, 보상·답례, 처음 흐름, 이름 붙이기)은 시안에 넣어 한꺼번에 확정받는다.

## 5. 개발 진행

**이 세션이 직접 한다.** 확정 시안(또는 세부 항목의 "끝났다고 보는 것")을 기준으로 구현하고, 시안에 없는 것은 더하지 않는다. 시안대로 못 하는 항목은 다르게 만들지 말고 이유와 함께 알린다.

- 로드맵 개발이면 대상 마일스톤과 세부 항목 고르기는 [references/plan.md](references/plan.md) "개발 플로우"를 따른다. 줄을 차례로 하고, 줄마다 바뀐 파일을 적어 둔다. `(사용자)` 표시 줄과 사람 테스트(`T1` 등)는 하지 않고 보고의 "사용자 몫"에 모은다.
- 프로젝트 고정 규칙(테스트 명령, 한 번에 하나만 도는 도구, 건드리면 안 되는 것, 태그 이름, 공개 배포 여부)은 [references/projects.md](references/projects.md)의 순서대로 찾아 따른다. 거기에 없을 때만 필요한 순간에 묻는다.
- **하위 세션은 처음 질문(2절)에서 맡기라고 했거나 사용자가 "세션 만들어서 해줘"라고 할 때만 쓴다.** 먼저 만들지 않는다. 쓰게 되면 [references/sessions.md](references/sessions.md)를 읽는다(브리프, 못 만들 때, 결과 확인). 대화의 앞부분이 요약되기 시작하면 "새 세션으로 넘길까요?"라고 한 번 제안한다.
- `Agent` 하위 에이전트는 새 세션이 아니다. 결과를 이번 턴에 바로 받는 일(조사, 나눠 쓰기, 검토 한 번)에 쓴다.
- **알아서 할 범위**가 "결재 빼고 알아서"면(기본값. 사용자가 "매 단계 확인"이라고 했으면 단계마다 멈춘다) 체크리스트 갱신과 판단 가능한 기획 결정까지 진행하고, 결정은 체크리스트에 기록한다. 결제, 계정 생성, 저장소 공개 전환처럼 되돌리기 어려운 일은 하지 않고 사용자에게 남긴다. git은 여기에 들어가지 않는다(2절).
- **사용자 취향인 결정은 "알아서"여도 사용자가 정한다.** 제품을 쓰는 사람이 보는 것(화면 문구, 보상·답례, 처음 흐름 순서, 이름 붙이기)과 쓰는 외부 서비스를 바꾸는 것이다. 시안에 없던 것이 생기면 [references/decisions.md](references/decisions.md) "사용자 취향인 결정"을 읽는다. 외부 자산·라이브러리·AI 모델·외부 서비스를 넣기 전에는 같은 문서 "라이선스·약관"을 읽는다(Claude가 먼저 보고, 사용자에게 확인을 넘기지 않는다).
- **고쳐 달라는 말을 받았을 때**: 말한 그 한 곳만 고치고 끝내지 않는다.
  - 사용자가 원칙을 말했으면("~전까지는 드러내지 마", "이름은 짧게") 두 번째 지적을 기다리지 않고 바로 그 원칙에 걸리는 곳을 코드와 문서에서 모두 찾아 한 번에 고친다. 일부러 남긴 곳은 까닭과 함께 목록으로 보인다. "이것도 원하시면 말씀해 주세요"로 하나씩 남기지 않는다. 사용자가 말한 원칙이 곧 확인이므로 시안을 다시 거치지 않고, 확정 시안과 달라진 항목은 시안 대조에 "다르게 됨(원칙: …)"으로 적는다. 저장 형식·규칙 시안·외부 서비스가 바뀌는 곳은 고치지 않고 남긴 목록에 둔다.
  - 원칙을 말하지 않은 지적이 같은 까닭으로 두 번째 오면, 고치면서 "제가 이해한 원칙"을 한 줄로 적고 같은 문제가 있는 곳을 "지금 → 바꿀 것" 목록으로 모두 보인 뒤 전부 바꿀지 고를지 묻는다. 원칙이 둘 이상으로 읽힐 때만 목록 전에 어느 쪽인지 먼저 묻는다. 자리 비움 중이면 묻지 않고 전부 바꾼 뒤 "확인해 주세요"에 짐작한 원칙과 그 목록을 둔다.
  - 바꿀 말이나 값을 새로 정해야 하면 지어내지 않고 근거를 찾는다(화면에 나오는 이름은 mockup.md "화면에 나오는 말").
  - 받은 원칙은 다음에도 지키도록 적어 둔다: 제품의 뜻에 닿으면 `concept.md` 맨 위 지킬 것 표에, 그 밖은 프로젝트 개발 문서(CLAUDE.md 등, 없으면 이어 하기 메모)에 한 줄. 어느 프로젝트에나 해당하는 취향이면 "내 방식"에 적는다.
- 로그인·클라우드 저장·결제·지도처럼 외부 서비스가 필요하면 [references/external-setup.md](references/external-setup.md)를 따른다. Claude는 계정을 만들거나 콘솔에 값을 넣지 않고, 비밀값은 어떤 저장소에도 넣지 않는다.

## 6. 테스트

만든 쪽과 확인하는 쪽이 같으므로, "됐어요" 한마디가 아니라 증거를 남긴다.

1. **시험**: 고친 기능에 닿는 테스트를 돌리고 명령·종료 코드·결과 줄을 그대로 적는다. 범위는 [references/test.md](references/test.md) "돌릴 테스트"(관련 테스트 먼저, 전체는 마일스톤 끝).
2. **범위**: 바뀐 파일이 맡은 범위 안인지 `git status`·`git diff`로 본다. 범위 밖을 건드렸으면 보고에 적는다.
3. **시안 대조**: 시안 항목마다 "됐음 / 안 됨 / 다르게 됨(이유)"을 적는다([references/mockup.md](references/mockup.md) "시안 대조"). 화면이면 실제 화면을 본다.
4. **위험한 변경 검토**: 위험한 변경(저장·네트워크처럼 여러 기능이 같이 쓰는 코드 · 형식·스키마·버전 번호 변경 · 인증·결제·비밀값에 닿는 코드 · 파일이나 데이터를 지우는 코드 · 자동 시험(CI) 없이 테스트도 새로 쓴 변경 · 규칙의 뜻을 바꾸는 문서 변경)은 `Agent` 검토 에이전트에 바뀐 내용과 기준만 주고 한 번 더 보게 한다. 내 요약은 주지 않는다. [references/test.md](references/test.md) "위험한 변경 검토"를 읽는다. 위험하지 않으면 1~3만 한다.

- 시험이 뒤에서 도는 동안 중간 보고로 일을 끝내지 않는다. 통과하면 받은 git 범위까지 이어서 한 뒤 보고한다. 머지 직전 확인처럼 원래 멈추는 곳은 그대로 멈춘다([references/test.md](references/test.md) "돌릴 테스트").
- 걸리면 개발로 돌아가 고친다. 검토 지적 가운데 사소한 것은 고치지 않고 보고의 "나중에"에 적는다([references/test.md](references/test.md) "검토 지적 나누기").
- 사용자가 "테스트 > 개선 > 커밋 > 테스트 반복"을 요청하면 [references/qa-loop.md](references/qa-loop.md)를 읽고 따른다.

## 7. 배포·머지

**처음 질문에서 받은 범위만큼, 또는 사용자가 시킨 만큼만 한다(2절).** 받은 것이 없으면 이 단계에 들어가지 않고, 마무리 보고에 "커밋·PR·머지는 말씀하시면 해요" 한 줄만 붙인다.

커밋·PR·머지를 하게 되면 [references/git.md](references/git.md)를 읽는다(커밋 메시지 꼴, PR 본문 네 칸, squash 머지, CI, 예외).

- 커밋 제목은 `<타입>: <결과 한 줄>`, 한 커밋 = 목적 하나.
- PR을 만들었으면 CI 결과를 기다려 확인한다. 머지는 6절 확인과 CI를 통과한 뒤에만 한다(잡이 대기 중이라 CI가 끝나지 않을 때는 git.md "CI 시간").
- main push가 곧 배포인 저장소는 "머지까지"를 받았어도 머지 직전에 한 번 확인받는다.
- 태그 꼴은 [references/rules.md](references/rules.md) "태그".

## 8. 보고·자리 비움·마무리

- **마무리 보고**는 네 칸이다: 무엇을 바꿨나 · 어떻게 확인했나(명령·종료 코드·결과 줄, 시안 대조) · 범위 밖에서 건드린 것 · 확인 못 한 것·남은 것. 사소한 지적이 있으면 "나중에" 칸을 더한다. 만들다가 새로 지은 화면 이름이 있으면 "새로 지은 말" 칸을 더한다(자리 · 쓴 말 · 근거). 끝에 다음 할 일을 번호로 적고 추천을 1번에 둔다. 사용자에게 가는 글(마무리 보고, 진행 물음의 답, PR 본문)에서 번호나 기호만으로 가리키지 않는다: "3단계", "A2", "M1-9"처럼 쓸 때는 "3단계(알림 설정 화면)"처럼 그것이 무엇인지 그 글에서 처음 나올 때 같이 적는다. 다른 참조 문서의 보고 예시가 번호만 적었어도 이 규칙을 따른다.
- **사용자에게 주는 명령은 어디서 쳐도 돌게 적는다.** 보고나 답에 사용자가 직접 칠 명령을 적을 때는 파일과 폴더를 전체 경로로 쓴다(`node tools/serve.js` ✗ → `node D:\work\shop\tools\serve.js`. 빈칸이 든 경로는 따옴표로 감싼다). 확인 칸에 증거로 적는 명령은 돌린 그대로 적는다. 그 폴더 안에서만 도는 명령(`npm run dev`처럼 폴더의 설정을 읽는 것)은 그 폴더로 가는 명령을 앞줄에 따로 적는다. 적기 전에 프로젝트 폴더가 아닌 곳에서 한 번 돌려 본다. 서버를 켜는 명령처럼 끝나지 않는 것과 무언가를 바꾸는 명령(배포·지우기·설치·git·로그인)은 돌리지 않고 경로가 있는지만 확인한다. 저장소에 남는 글(README, 개발 문서, 이어 하기 메모, 커밋 메시지, PR 본문)에는 공개든 비공개든 전체 경로를 쓰지 않고 "저장소 폴더에서"라고 적은 뒤 상대 경로를 쓴다.
- **"진행중이니?", "남은 거?", "얼마나 걸려?"**에는 늘 같은 꼴로 답한다. 이런 물음이 오면 [references/progress.md](references/progress.md) "진행 물음 꼴"을 읽는다. 숫자는 직접 보고 적고, 예상 시간을 모르면 지어내지 않는다. 큰 단계 알림은 "내 방식"에 켬일 때만 한다(같은 문서 "큰 단계 알림").
- **자리 비움**: 사용자가 "병원 다녀올게", "자러 갈게", "다되면 마무리해줘"라고 하면 [references/wrap-up.md](references/wrap-up.md) "자리 비움"을 따른다. 떠나기 전에 처음 질문과 시안을 확정받고, 그 뒤로는 선택 UI를 띄우지 않는다. 되돌릴 수 있는 것은 추천대로 정해 적고, 되돌리기 어려운 것은 "돌아오시면 정할 것"에 모은다.
- **마무리**: "다되면 문서 정리하고 마무리해줘"라고 했거나, 자리 비움 중 일이 다 끝났거나, 마일스톤이 끝났으면 [references/wrap-up.md](references/wrap-up.md) "마무리"를 한다: 전체 테스트(마일스톤 끝) → 시안 대조 → 문서 정리(바뀐 것만) → 이어 하기 메모 → 보고. 마일스톤이 끝나면 기획의 갱신 플로우(시나리오 🔜 → ✅, 점수 다시 계산)를 돈다([references/plan.md](references/plan.md)).
