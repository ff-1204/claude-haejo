# 하위 세션으로 맡기기

사용자는 작업마다 하위 세션을 만들어 알아서 진행하는 방식을 좋아한다. 이 세션(부모)은 작업을 나누고, 안내(브리프)를 쓰고, 결과를 확인해 짧게 보고한다. 코드를 직접 고치는 건 하위 세션의 몫이다.

## 0. 시작 전에 묻기 (첫 실행 때 한 번, UI로)

시작 전에 정할 것은 글로 묻지 않고 `AskUserQuestion`(선택 버튼 UI)으로 한 번에 묻는다. 한 번에 최대 4개까지 묻고, 더 있으면 한 번 더 부른다. 추천을 첫 번째 선택지에 두고 라벨 끝에 "(추천)"을 붙인다.

- 사용자 요청이나 메모리에 이미 답이 있는 질문은 빼고, 남은 것만 묻는다.
- 받은 답은 이번 실행 내내 쓴다. 브리프와 반복 기록에 적어 두고, 중간에 다시 묻지 않는다.

물어볼 후보:

| 질문 | 선택지 예 |
|---|---|
| 테스트·검토 세션 모델 | Opus / 지금 세션과 같은 모델 / Sonnet |
| 구현 세션 모델 | 지금 세션과 같은 모델 / Opus / Fable |
| 알아서 할 범위 | 결재 빼고 알아서(커밋·push·태그 포함) / 커밋까지만, push·태그는 물어보기 / 매 단계 확인 |
| 시간·끝내는 기준 (반복 작업일 때) | 6시간 / 3시간 / 체크리스트 남은 항목 끝까지 |
| 컴퓨터 사용 허락 (실제 실행해 보는 테스트일 때) | 허락, 그동안 PC 안 씀 / 허락 안 함(자동 테스트·스크린샷만) |
| 프로젝트별로 정할 것 | 예: 태그 이름, 공개 배포 여부 |

자동 이벤트로 시작된 턴이라 사용자가 자리에 없을 수 있으면, 묻지 말고 이전 답을 쓴다. 이전 답이 없으면 그 질문은 보고에 남긴다.

## 1. 나누기

- 하위 세션 하나 = 끝이 분명한 작업 하나: 체크리스트 항목 하나 또는 묶음 하나, 테스트 한 회차, 조사 하나.
- 같은 파일을 건드리는 작업은 동시에 돌리지 않는다.
- 한 번에 하나만 돌 수 있는 도구(예: Unity 배치, 같은 포트의 개발 서버, 같은 DB)를 쓰는 세션은 순서대로 하나씩 돌린다. 프로젝트마다 무엇이 해당하는지는 프로젝트 규칙([references/projects.md](references/projects.md))에서 찾는다.
- 부모가 몇 번의 도구 호출로 끝낼 수 있는 일(질문 답, 파일 하나 수정, 상태 확인)은 세션을 만들지 않고 여기서 한다.

## 2. 브리프 쓰기

하위 세션은 브리프만 보고 일한다. 매번 아래 순서로 쓴다(한국어).

1. **배경**: 프로젝트, 저장소 경로, 브랜치·worktree, 지금 단계(마일스톤, 마지막 태그·커밋).
2. **고정 규칙**: [references/projects.md](references/projects.md)의 순서대로 찾아서 그대로 옮긴다.
3. **할 일**: 체크리스트 번호와 함께. 시나리오(여정)를 먼저 적고 시작하라고 쓴다.
4. **하지 말 일**: 범위 밖 항목, 사용자 항목(I13·T), 번호 바꾸기, 결제.
5. **끝난 모습**: 통과해야 할 확인 명령, 체크리스트 ✅ 표시, 커밋(목적별) 여부, push·태그 여부.
6. **기다리는 법**: "백그라운드 작업 알림만 믿지 말고 결과 파일이나 프로세스 종료를 직접 확인할 것."
7. **보고 형식**: 사용자는 휴대폰 Remote Control로 볼 때가 많다. 마무리 메시지에 한 일, 커밋·태그, 남은 것, 선택지(번호, 추천은 1번)를 글로 적을 것.

## 3. 시작하기

- `mcp__ccd_session__start_session`, context는 `"fresh"`(브리프가 전부 담는다), title은 "개선 2회차 + 이동·리스폰"처럼 무엇을 하는지 바로 보이게.
- 사용자가 맡기라고 했으면 initiation `"user_asked"`.
- 모델: 0절에서 정한 테스트·검토 모델과 구현 모델을 쓴다.
- 직전 세션의 보고서나 대화를 통째로 넘기지 않는다. 필요한 사실만 브리프에 요약한다(편향 방지).
- **자동 이벤트(세션 알림 등)로 시작된 턴에서는 세션 시작이 막힌다.** 그때는 같은 브리프로 `Agent` 서브에이전트를 돌린다. 사용자가 카드를 누르지 않아도 계속 돌아가게 하기 위해서다.

## 4. 기다리는 동안

- 폴링하지 않는다. 하위 세션이 턴을 끝내면 앱이 알려 준다.
- 하위 세션이 idle인데 일이 안 끝났으면(예: 오래 걸리는 빌드·테스트 알림을 못 받고 멈춤) `list_events`로 마지막 상태를 보고, 프로세스를 확인한 뒤 `SendMessage`로 "결과 파일을 직접 확인하고 이어서 진행" 하라고 보낸다.
- 하위 세션이 질문하면 0절의 답과 사용자 취향(아래 7절)으로 답할 수 있으면 답한다. 결제나 되돌리기 어려운 공개 결정만 사용자에게 묻는다. 이때도 `AskUserQuestion` UI로 묻는다.

## 5. 결과 확인

하위 세션의 보고는 증거가 아니다. 보고하기 전에 직접 본다.

- `git log --oneline -5`, `git status -sb`, 변경 diff 요약
- 해당 테스트 명령 결과(또는 보고서 파일)
- 체크리스트에서 그 번호의 표시

다른 점이 있으면 같은 세션에 `SendMessage`로 고치게 한다(새 세션을 만들지 않는다).

## 6. 테스트 반복(QA 루프)

사용자가 "테스트 > 개선 > 커밋 > 테스트 반복"을 요청하면 [references/qa-loop.md](references/qa-loop.md)를 읽고 따른다.

## 7. 알아서 할 범위

0절에서 "결재 빼고 알아서"를 골랐거나 사용자가 그렇게 말했으면:
- 커밋(목적별), push, 태그, 체크리스트 갱신, 판단 가능한 기획 결정까지 진행한다.
- 기획 결정은 비슷한 게임을 조사해 이 프로젝트에 맞는 쪽으로 정하고, 결정 사항을 체크리스트에 기록한다.
- 결제, 계정 생성, 저장소 공개 전환처럼 되돌리기 어려운 일은 하지 않고 사용자에게 남긴다.

그 말이 없으면 커밋·push·태그는 사용자가 말할 때만 한다("커밋만", "아직 푸시하지 마"를 그대로 따른다).

## 8. 보고

짧게, 휴대폰에서 읽기 좋게 쓴다. 세션은 `[제목](#local_…)` 링크로 적는다.

- 끝난 것: 세션, 커밋·태그, 체크리스트 번호
- 확인한 것 / 확인 못 한 것
- 다음 작업: 번호 붙은 선택지, 추천은 1번

## 9. 기획에서 이어질 때

마일스톤 세부 항목(한 줄 = 한 작업 단위)을 맡길 때는 그 줄의 체크리스트 번호와 "끝났다고 보는 것"을 브리프의 할 일·끝난 모습에 그대로 옮긴다. 마일스톤이 끝나면 시나리오의 🔜를 ✅로 바꾸고 점수를 다시 계산한다. 전체 과정: https://github.com/ff-1204/claude-config/tree/main/playbooks/persona-roadmap
