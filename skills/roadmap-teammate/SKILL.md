# 하위 세션으로 맡기기

사용자는 작업마다 하위 세션을 만들어 알아서 진행하는 방식을 좋아한다. 이 세션(부모)은 작업을 나누고, 안내(브리프)를 쓰고, 결과를 확인해 짧게 보고한다. 코드를 직접 고치는 건 하위 세션의 몫이다.

## 0. 시작 전에 묻기 (첫 실행 때 한 번, UI로)

시작 전에 정할 것은 글로 묻지 않고 `AskUserQuestion`(선택 버튼 UI)으로 한 번에 묻는다. 한 번에 최대 4개까지 묻고, 더 있으면 한 번 더 부른다. 추천을 첫 번째 선택지에 두고 라벨 끝에 "(추천)"을 붙인다.

- **커밋·push·PR·머지·태그는 사용자 권한이다.** 스킬을 쓸 때마다 선택 UI로 묻고 답한 만큼만 한다. 메모리·지난 답·"결재 빼고 알아서"로 대신하지 않는다. 이 질문은 빼지 않는다. "커밋만", "아직 푸시하지 마"처럼 사용자가 한 말은 그대로 따른다. 권한을 받지 않은 커밋·push·PR·머지·태그가 필요해지면 그 자리에서 선택 UI로 묻는다. 자리를 비워 물을 수 없으면 하지 않고 "돌아오시면 정할 것"에 둔다.
- **커밋 꼬리표**(커밋 끝의 `Co-Authored-By: Claude …` 줄)도 권한처럼 매번 같은 화면에서 묻고, 메모리·지난 답으로 대신하지 않는다. 자리를 비워 물을 수 없으면 기본(남기기)으로 한다.
- 다른 질문은 사용자 요청이나 메모리에 이미 답이 있으면 빼고, 남은 것만 묻는다.
- **모델은 프로젝트마다 처음 한 번만 묻는다.** 답을 그 프로젝트 메모리에 "테스트 모델 / 구현 모델"로 남기고, 다음부터는 묻지 않고 쓴다(보고에 어떤 모델인지만 적는다). 사용자가 말로 바꾸면 메모리도 고친다.
- 받은 답은 이번 실행 내내 쓴다. 브리프와 반복 기록에 적어 두고, 중간에 다시 묻지 않는다.

물어볼 후보:

| 질문 | 선택지 예 |
|---|---|
| 테스트·검토 세션 모델 (**프로젝트마다 처음 한 번**) | Opus / 지금 세션과 같은 모델 / Sonnet |
| 구현 세션 모델 (**프로젝트마다 처음 한 번**) | 지금 세션과 같은 모델 / Opus / Fable |
| **커밋·push·PR·머지·태그 권한 (항상 묻기)** | PR까지 맡기고 머지는 부모가 확인 뒤 묻기 / 머지까지 맡기기(이번 실행만) / 그때마다 묻기. 첫째·둘째는 하위 세션이 자기 브랜치에 커밋·push하고 PR을 만드는 것까지 맡긴다. 태그는 머지와 같이 정한다. GitHub 원격이 없으면 13절 예외대로 커밋 권한만 묻는다 |
| **커밋 꼬리표 (항상 묻기, 권한 질문과 같은 화면)** | Co-Authored-By 남기기(추천·기본) / 빼고 본문에 "<모델>로 진행함" 한 줄 / 둘 다 빼기 |
| 알아서 할 범위 (커밋·push·PR·머지·태그 빼고) | 결재 빼고 알아서 / 매 단계 확인 |
| 시간·끝내는 기준 (반복 작업일 때) | 6시간 / 3시간 / 체크리스트 남은 항목 끝까지 |
| 컴퓨터 사용 허락 (실제 실행해 보는 테스트일 때) | 허락, 그동안 PC 안 씀 / 허락 안 함(자동 테스트·스크린샷만) |
| 프로젝트별로 정할 것 | 예: 태그 이름, 공개 배포 여부 |

사용자가 자리를 비웠으면(10절) 묻지 않는다. 자동 이벤트로 시작된 턴이라 사용자가 자리에 없을 수 있으면, 묻지 말고 이전 답을 쓴다. 이전 답이 없으면 그 질문은 보고에 남긴다.

## 1. 나누기

- 하위 세션 하나 = 끝이 분명한 작업 하나 = 브랜치 하나 = PR 하나(13절): 체크리스트 항목 하나 또는 묶음 하나, 테스트 한 회차, 조사 하나. 코드를 바꾸지 않는 세션(테스트 회차, 조사)은 PR을 만들지 않는다.
- 같은 파일을 건드리는 작업은 동시에 돌리지 않는다.
- 한 번에 하나만 돌 수 있는 도구(예: Unity 배치, 같은 포트의 개발 서버, 같은 DB)를 쓰는 세션은 순서대로 하나씩 돌린다. 프로젝트마다 무엇이 해당하는지는 프로젝트 규칙([references/projects.md](references/projects.md))에서 찾는다.
- 부모가 몇 번의 도구 호출로 끝낼 수 있는 일(질문 답, 상태 확인, 기록 고치기)은 세션을 만들지 않고 여기서 한다. 단 코드를 바꾸는 작은 고침은 아래 "작은 고침" 방식을 따른다.
- **작은 고침은 묶는다.** 문구, 표시 조건, 순서처럼 한두 파일만 고치는 요청이 연달아 오면 요청마다 세션을 만들지 않는다.
  - 첫 요청에 "빠른 고침" 세션 하나를 만들고(제목 예: "빠른 고침 묶음 — 첫걸음 문구 외"), 이어 오는 작은 요청은 그 세션에 `SendMessage`로 붙인다. 이 세션에는 0절을 다시 묻지 않고 지난 답을 쓴다. 다른 세션과 같은 파일을 건드리면 그 세션이 끝난 뒤에 붙인다.
  - 그 세션은 (0절 권한이 있으면) 자기 브랜치에서 요청마다 목적별 커밋을 하고, 첫 요청 때 "빠른 고침" PR 하나를 만들어 이후 커밋을 거기에 더한다(PR 본문도 갱신). **머지는 부모가 5절 확인 항목을 본 뒤 0절 권한대로 묶어서 한 번 한다**(사용자가 "지금 배포"라고 하거나, 30분 넘게 새 요청이 없거나, 큰 작업을 시작하기 전). "지금 배포"는 빠른 고침 PR만 머지하고, 진행 중인 큰 작업은 끝난 뒤에. 머지 뒤 그 세션을 보관한다(13절).
  - 화면·흐름이 크게 바뀌거나 저장 형식·경제 규칙을 건드리면 작은 고침이 아니다. 따로 세션을 만든다.

## 2. 브리프 쓰기

하위 세션은 브리프만 보고 일한다. 매번 아래 순서로 쓴다(한국어).

1. **배경**: 프로젝트, 저장소 경로, 브랜치·worktree, 지금 단계(마일스톤, 마지막 태그·커밋).
2. **고정 규칙**: [references/projects.md](references/projects.md)의 순서대로 찾아서 그대로 옮긴다.
3. **할 일**: 체크리스트 번호와 함께. 시나리오(여정)를 먼저 적고 시작하라고 쓴다.
4. **하지 말 일**: 범위 밖 항목, 사용자 항목(I13·T), 번호 바꾸기, 결제.
5. **끝난 모습**: 통과해야 할 확인 명령, 체크리스트 ✅ 표시. 커밋·push·PR은 0절 권한 답을 그대로 적는다(예: "커밋은 목적별로. 브랜치를 push하고 `gh pr create`로 기본 브랜치 대상 PR을 만들 것. 본문은 13절 꼴. 머지·태그는 하지 말 것"). 커밋 꼬리표 답도 그대로 적는다. 추가 피드백(부모의 `SendMessage`, PR 리뷰 댓글, CI 실패)은 같은 PR에 커밋을 더해 고치고 본문을 갱신하라고 쓴다. `gh`가 없거나 인증이 안 되면 브랜치 push까지 하고 그 사실을 보고하게 한다. 권한이 없으면 하위 세션은 변경을 커밋하지 않고 남긴 채 보고한다.
6. **기다리는 법**: "백그라운드 작업 알림만 믿지 말고 결과 파일이나 프로세스 종료를 직접 확인할 것."
   외부 서비스를 쓰는 작업이면 "비밀값은 저장소에 넣지 않는다"와 외부 준비 안내서 경로도 넣는다(12절).
7. **보고 형식**: 사용자는 휴대폰 Remote Control로 볼 때가 많다. 마무리 메시지에 PR 링크, 한 일, 커밋, 남은 것, 선택지(번호, 추천은 1번)를 글로 적을 것.

## 3. 시작하기

- `mcp__ccd_session__start_session`. 도구 목록에 이름만 있으면(deferred) 먼저 `ToolSearch`로 `select:mcp__ccd_session__start_session`을 불러온다. 안 보인다고 `Agent`로 대신하지 않는다.
- context는 `"fresh"`(브리프가 전부 담는다), title은 "개선 2회차 + 이동·리스폰"처럼 무엇을 하는지 바로 보이게.
- 사용자가 맡기라고 했으면 initiation `"user_asked"`. 사용자가 휴대폰(Remote Control)으로 봐도 바로 시작된다. Remote Control은 `Agent`로 바꿀 이유가 아니다.
- 코드를 바꾸는 세션은 `use_worktree: true`로 자기 worktree(브랜치)에서 일하게 한다. GitHub 원격이 없거나 git이 아닌 프로젝트는 13절 예외를 따른다.
- 모델: 0절에서 정한 테스트·검토 모델과 구현 모델을 쓴다.
- 직전 세션의 보고서나 대화를 통째로 넘기지 않는다. 필요한 사실만 브리프에 요약한다(편향 방지).
- **자동 이벤트 턴**: 하위 세션이 끝난 알림(`<side-sessions-event>`) 턴에서 사용자가 이미 맡긴 다음 단계는 그대로 하위 세션으로 시작한다(앱이 허용하는 경우).
- **앱이 시작을 막으면 `Agent`로 대신하지 않는다.** 다음 작업을 `own_initiative` 카드로 남기고, 보고에 "다음 작업은 카드를 누르거나 '이어 해줘'라고 하면 시작" 한 줄을 적는다. 자리 비움(10절) 중이면 "돌아오시면 정할 것"에 모은다.
- `Agent` 하위 에이전트는 결과를 이번 턴에 바로 받는 일(조사, 나눠 쓰기, 검토 한 번)에만 쓴다. 브랜치·PR로 끝나는 구현 작업은 하위 세션으로만 맡긴다.

## 4. 기다리는 동안

- 폴링하지 않는다. 하위 세션이 턴을 끝내면 앱이 알려 준다.
- 하위 세션이 idle인데 일이 안 끝났으면(예: 오래 걸리는 빌드·테스트 알림을 못 받고 멈춤) `list_events`로 마지막 상태를 보고, 프로세스를 확인한 뒤 `SendMessage`로 "결과 파일을 직접 확인하고 이어서 진행" 하라고 보낸다.
- 하위 세션이 질문하면 0절의 답과 사용자 취향(아래 7절)으로 답할 수 있으면 답한다. 결제나 되돌리기 어려운 공개 결정만 사용자에게 묻는다. 이때도 `AskUserQuestion` UI로 묻는다. 사용자가 자리를 비웠으면(10절) 묻지 않고 "돌아오시면 정할 것"에 모은다.

## 5. 결과 확인 (PR 확인 항목 4개)

부모는 코드를 다시 읽지 않는다. PR 요약과 아래 네 가지만 보고 머지할지 정한다. 하위 세션의 보고는 증거가 아니라는 원칙은 2~4번이 맡는다(`gh pr view <번호> --json body,files,mergeable,statusCheckRollup`, `gh pr checks <번호>`).

1. **PR 최종 요약**: 본문이 13절 꼴 네 칸을 다 채웠나.
2. **CI·테스트 통과**: CI가 있으면 모두 통과. 없으면 본문 "어떻게 확인했나"의 명령을 그 PR 브랜치에서 한 번 돌려 본다.
3. **범위 안**: 바뀐 파일 목록이 브리프 범위 안이고, "하지 말 일"의 파일을 건드리지 않았다.
4. **머지 가능**: 기본 브랜치와 충돌이 없다.

하나라도 걸리면 그 세션에 `SendMessage`로 같은 PR 안에서 고치게 한다(새 세션을 만들지 않는다). 다 통과해 사용자에게 머지를 물을 때는 13절 "보고 꼴"로 쓴다. 테스트 회차·조사처럼 PR이 없는 세션은 보고서 파일과 확인 명령 결과를 직접 본다.

## 6. 테스트 반복(QA 루프)

사용자가 "테스트 > 개선 > 커밋 > 테스트 반복"을 요청하면 [references/qa-loop.md](references/qa-loop.md)를 읽고 따른다.

## 7. 알아서 할 범위

0절에서 "결재 빼고 알아서"를 골랐거나 사용자가 그렇게 말했으면:
- 체크리스트 갱신, 판단 가능한 기획 결정까지 진행한다. 커밋·push·PR·머지·태그는 여기에 들어가지 않는다(0절 권한 답대로만).
- 기획 결정은 비슷한 게임을 조사해 이 프로젝트에 맞는 쪽으로 정하고, 결정 사항을 체크리스트에 기록한다. 단 아래 "사용자 취향인 결정"은 빼고.
- 결제, 계정 생성, 저장소 공개 전환처럼 되돌리기 어려운 일은 하지 않고 사용자에게 남긴다.

**사용자 취향인 결정은 "알아서"여도 선택 UI로 묻는다.** 되돌릴 수는 있지만 사용자가 분명한 취향을 가진 것들이다.
- **플레이어(사용자)가 보는 것**: 화면 문구, 보상·답례 같은 주고받는 것의 내용, 처음 흐름(첫걸음·튜토리얼) 순서, 이름 붙이기. 내부 구조·코드·데이터 형식은 Claude가 정한다.
- **쓰는 외부 서비스를 바꾸는 것**: 같은 일을 하는 무료 대안으로 바꾸기 등(references/external-setup.md).
- 물을 때 선택지 2~3개와 추천을 주고, 문구면 실제 문장을 선택지에 그대로 쓴다.
- 사용자가 자리를 비웠으면(10절) 플레이어가 보는 것은 추천대로 하되 **보고 맨 위 "확인해 주세요"**에 바꾼 문장·내용을 그대로 보인다. 외부 서비스 바꾸기는 하지 않고 그 줄을 ⏸로 둔다.
## 8. 보고

짧게, 휴대폰에서 읽기 좋게 쓴다. 세션은 `[제목](#local_…)` 링크로 적는다.

- 끝난 것: 세션, PR 링크(머지했는지), 태그, 체크리스트 번호
- 확인한 것 / 확인 못 한 것
- 다음 작업: 번호 붙은 선택지, 추천은 1번

## 9. 기획에서 이어질 때

한 주제 기획(rules.md "기획 크기")에서 온 세부 항목은 체크리스트 번호가 그 주제 절(예: `P28-02`) 아래에 있다. 마일스톤 세부 항목(한 줄 = 한 작업 단위)을 맡길 때는 그 줄의 체크리스트 번호와 "끝났다고 보는 것"을 브리프의 할 일·끝난 모습에 그대로 옮긴다. 마일스톤이 끝나면 `roadmap` 스킬의 갱신 플로우(시나리오 🔜 → ✅, 점수 다시 계산)를 부른다. 이 스킬은 `roadmap`의 개발 플로우에서도 불린다.

## 10. 자리 비움

사용자가 "병원 다녀올게", "자러 갈게", "다되면 마무리해줘"처럼 자리를 비우면 [references/wrap-up.md](references/wrap-up.md) "자리 비움"을 따른다: 선택 UI로 묻지 않고, 되돌릴 수 있는 것은 추천대로 정해 적고, 되돌리기 어려운 것은 "돌아오시면 정할 것"에 모은다. 맡은 일이 끝나면 마무리하고 멈춘다.

## 11. 마무리

"다되면 문서 정리하고 마무리해줘"라고 했거나, 자리 비움 중 일이 다 끝났거나, 마일스톤이 끝났으면 [references/wrap-up.md](references/wrap-up.md) "마무리"를 한다: 전체 확인 → 머지·태그 → 문서 정리(README·개발 문서·체크리스트·기획 문서·QA 기록) → 메모리 → 저장소 안 이어 하기 메모 → 돌아오셨을 때 보고.

## 12. 외부 준비와 비밀값

로그인·클라우드 저장·결제·지도처럼 외부 서비스가 필요하면 [references/external-setup.md](references/external-setup.md)를 따른다: 하위 세션을 시작하기 전에 사용자가 콘솔에서 할 일을 단계별 안내서(넣을 값, 비용, 자주 나는 오류)로 먼저 쓰고, 그동안 외부 값이 필요 없는 부분을 브랜치에서 진행한다. 비밀값은 어떤 저장소에도 넣지 않는다.

## 13. PR과 머지

- **한 작업 = 브랜치 하나 = PR 하나.** 하위 세션은 자기 worktree에서 일하고 끝나면 기본 브랜치 대상 PR을 만든다. 코드 개선·테스트·검증·추가 피드백(부모의 `SendMessage`, PR 리뷰 댓글, CI 실패)은 모두 같은 PR에 커밋을 더해 처리한다. 필요하면 검토 세션이 같은 PR을 리뷰한다.
- **PR 본문 = 최종 요약.** 하위 세션이 쓰고 커밋을 더할 때마다 갱신한다.
  ```
  ## 무엇을 바꿨나
  - <체크리스트 번호> <한 줄>
  ## 어떻게 확인했나
  - `<명령>` → <결과>
  ## 범위 밖에서 건드린 것
  - 없음
  ## 확인 못 한 것·남은 것
  - …
  ```
- **머지는 부모가 한다.** 하위 세션은 PR까지만. 부모는 5절 확인 항목 4개를 본 뒤 0절 권한대로 머지한다(추천 답이면 사용자에게 선택 UI로 묻고 머지). 태그는 머지 뒤 기본 브랜치에 단다.
- **머지를 물을 때 보고 꼴.** 사용자가 머지 전에 결과를 다 알게 쓴다. 설치·배포처럼 머지 뒤에 생기는 일도 먼저 적는다.
  ```
  **무엇**: <PR 링크> — <체크리스트 번호> <한 줄>
  **확인**: 요약 통과(4칸) · 테스트 통과(CI / 직접 돌림) · 범위 통과(파일 3개, 범위 밖 없음) · 충돌 없음
  **확인 못 한 것·남은 것**: <PR 본문 마지막 칸 그대로, 사람이 직접 해 볼 것 포함>
  **머지하면**: 배포 여부 · 태그 · 따로 할 설치·반영(예: `./install.sh`)
  1) 머지하고 정리(설치·세션 보관) (추천) 2) 머지만 3) 아직 안 함(PR 열어 두기)
  ```
  - 확인 4개는 항목마다 통과/걸림을 적는다. 걸린 게 있으면 묻지 않고 5절대로 고치게 한다.
  - 선택지는 선택 UI로도 묻는다. 고른 대로 머지·설치·보관을 하고 결과를 한 줄로 보고한다.
  - 0절에서 머지까지 맡겼으면(아래 배포 예외 빼고) 묻지 않고 머지하고, 같은 꼴(선택지 빼고)로 머지 뒤 보고한다.
- 머지 뒤 그 하위 세션을 보관한다. 되돌릴 수 있어 묻지 않는다. 사용자가 "그대로 둬"라고 하면 남긴다.
- **PR이 여럿이면 하나씩 머지한다.** 먼저 머지된 것과 충돌하면 그 PR의 세션이 기본 브랜치를 받아 고친 뒤 머지한다.
- 예외:
  - GitHub 원격이 없거나 git이 아닌 프로젝트: PR 없이 지금처럼 커밋만 한다(5절은 `git log`·diff 요약·테스트 결과로 본다).
  - 작은 고침 묶음(1절): "빠른 고침" PR 하나에 모아 한 번 머지한다.
  - main push가 곧 배포인 프로젝트: 머지가 배포다. 0절에서 머지까지 맡겼어도 머지 때 따로 선택 UI로 확인한다.
  - 한 번에 하나만 도는 도구(1절): worktree를 나눠도 세션은 순서대로 돌린다.
  - 서로 기대는 작업: 앞 PR이 머지된 뒤 다음 세션을 시작한다.
