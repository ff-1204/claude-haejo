# 하위 세션으로 맡기기

사용자는 작업마다 하위 세션을 만들어 알아서 진행하는 방식을 좋아한다. 이 세션(부모)은 작업을 나누고, 안내(브리프)를 쓰고, 결과를 확인해 짧게 보고한다. 코드를 직접 고치는 건 하위 세션의 몫이다.

**기본값과 "내 방식".** 이 스킬에 적힌 보고 꼴·묻는 빈도·알림·디자인 방식·시험 되풀이 횟수는 누구에게나 무난한 기본값이다. 사용자가 `references/projects.local.md`의 "내 방식" 절(이 PC에만 있는 파일, [projects.md](references/projects.md) 템플릿)에 다르게 적었으면 그쪽을 따른다. 사용자가 말로 방식을 바꾸면 그 절에 적어 두고 다음 세션부터도 쓴다. 단 커밋·push·PR·머지·태그를 묻지 않고 하게 하는 설정은 "내 방식"으로도 할 수 없다(아래 0절).

## 0. 시작 전에 묻기 (첫 실행 때 한 번, UI로)

**세션마다 묻는 것은 커밋·push·PR·머지 권한 하나뿐이다.** 나머지는 묻지 않고 기본값을 쓴다(아래 "기본값"). 물을 때는 글로 묻지 않고 `AskUserQuestion`(선택 버튼 UI)으로 한 화면에 묻는다. 추천을 첫 번째 선택지에 두고 라벨 끝에 "(추천)"을 붙인다.

**권한: 커밋·push·PR·머지·태그는 사용자 권한이다.** 이 규칙의 원본은 여기다(루트 CLAUDE.md, roadmap rules.md "묻기"는 여기를 가리킨다).

| 경우 | 규칙 |
|---|---|
| 언제 묻나 | **세션마다 처음 한 번** 선택 UI로 묻고, 답한 만큼만 한다. |
| 같은 세션 안 | 받은 답을 끝까지 쓰고 다시 묻지 않는다. |
| 다시 묻는 곳 | 사용자가 직접 연 새 세션, 다른 저장소. |
| 대신 못 하는 것 | 메모리, 다른 세션의 답, "결재 빼고 알아서", "내 방식". |
| 브리프로 시작한 세션 | 하위 세션, 넘겨받은 부모 세션은 새 세션이어도 다시 묻지 않는다. 브리프에 적힌 답을 사용자 답으로 따르고, 브리프에 없는 권한만 묻는다. |
| 브리프 쓸 때 | 그래서 받은 권한 답과 쓴 꼬리표 값을 빠짐없이 적는다. |
| 사용자가 한 말 | "커밋만", "아직 푸시하지 마"처럼 한 말은 그대로 따른다. |
| 받지 않은 권한이 필요해지면 | 그 자리에서 선택 UI로 묻는다. |
| 물을 수 없을 때 | 자리를 비웠으면 하지 않고 "돌아오시면 정할 것"에 둔다. |
| 태그 | **사용자가 달아 달라고 할 때만 단다.** 권한 질문에 넣지 않는다. 마일스톤이 끝나도 먼저 달거나 권하지 않는다. |

**권한 질문 선택지.** PR까지 맡기고 머지는 부모가 확인 뒤 묻기(추천) / 머지까지 맡기기(이번 실행만) / 그때마다 묻기. 첫째·둘째는 하위 세션이 자기 브랜치에 커밋·push하고 PR을 만드는 것까지 맡긴다. 태그는 여기서 묻지 않는다(위 "태그"). GitHub 원격이 없으면 13절 예외대로 커밋 권한만 묻는다.

**시간·끝내는 기준만은 같은 화면에서 묻는다.** 테스트 반복처럼 끝이 정해지지 않은 일인데 사용자 말에 시간이나 끝내는 기준이 없으면, 권한 질문과 같은 화면에서 묻는다(선택지 예: 6시간 / 3시간 / 체크리스트 남은 항목 끝까지). 끝없이 도는 것을 기본값으로 정할 수 없어서다.

**기본값.** 나머지는 묻지 않는다. 사용자가 말했거나 메모리·"내 방식"(`projects.local.md`)에 적혀 있으면 그 값을 쓰고, 없으면 아래 기본값을 쓴다.

| 항목 | 기본값 |
|---|---|
| 커밋 꼬리표 | `Co-Authored-By` 남기기 |
| 테스트·검토 모델, 구현 모델 | 지금 세션과 같은 모델 |
| 알아서 할 범위 | 결재 빼고 알아서(7절) |
| 개발 범위 (개발 플로우일 때) | 이 마일스톤만 |
| 머지 뒤 하위 세션 정리 | 보관(되돌릴 수 있음, 13절 "머지 뒤 정리") |
| 컴퓨터 사용 (실제 실행해 보는 테스트일 때) | 허락 안 함(자동 테스트·스크린샷만) |

- 쓴 값은 시작 보고에 "기본값으로 정한 것" 한 줄로 보인다.
- 사용자가 말로 바꾸면 그대로 따르고 "내 방식"이나 메모리에 적는다.
- 정한 값은 이번 실행 내내 쓴다. 브리프와 반복 기록에 적어 두고, 중간에 다시 묻지 않는다.

**커밋 꼬리표**(커밋 끝의 `Co-Authored-By: Claude …` 줄)는 권한과 같은 급이 아니다. 세션마다 묻지 않고 "내 방식"의 값(남기기 / 빼고 본문에 "<모델>로 진행함" 한 줄 / 둘 다 빼기)을 쓴다. 적힌 값이 없으면 남기기다. 브리프로 시작한 세션은 브리프에 적힌 값을 따른다.

**프로젝트별로 정할 것**(태그 이름, 공개 배포 여부)은 프로젝트 규칙([references/projects.md](references/projects.md))에서 찾고, 없을 때만 필요한 순간에 묻는다.

**새 버전 안내.** 시작할 때 `node ~/.claude/skills/roadmap/scripts/check-update.js`를 한 번 돌린다. 한 줄이 나오면 마무리 보고 끝에 그대로 붙이고, 스스로 업데이트하지 않는다. "내 방식"에 `새 버전 안내: 끔`이면 돌리지 않는다.

**묻지 않을 때.**
- 사용자가 자리를 비웠으면(10절) 묻지 않는다.
- 자동 이벤트로 시작된 턴이라 사용자가 자리에 없을 수 있으면, 묻지 말고 이전 답을 쓴다. 이전 답이 없으면 그 질문은 보고에 남긴다.

## 1. 나누기

- 끝이 분명한 작업 하나 = 브랜치 하나 = PR 하나(13절): 체크리스트 항목 하나 또는 묶음 하나, 테스트 한 회차, 따로 오래 하는 조사 하나. 하위 세션은 작업 하나에 하나가 기본이고, 마일스톤 일은 아래 규칙대로 마일스톤마다 하나다. 코드를 바꾸지 않는 세션(테스트 회차, 조사)은 PR을 만들지 않는다.
- 결과를 이번 턴에 바로 쓰는 조사(답에 필요한 사실 찾기, 비교 한 번)는 하위 세션이 아니라 `Agent` 서브에이전트로 한다(3절).
- 같은 파일을 건드리는 작업은 동시에 돌리지 않는다.
- **마일스톤 번호가 바뀌면 새 세션, 같은 마일스톤의 다음 줄은 그 세션에 이어 맡긴다**(`SendMessage`, 줄마다 브랜치·PR은 따로). 마일스톤 세션을 만들거나 이어 맡길 때 [references/splitting.md](references/splitting.md) "마일스톤 세션"을 읽는다.
- **세션이나 부모 대화의 앞부분이 요약되기 시작하면 새 세션으로 넘긴다.** 그때 [references/splitting.md](references/splitting.md) "세션이 무거워졌을 때"를 읽는다.
- 한 번에 하나만 돌 수 있는 도구(예: 게임 엔진 배치 실행, 같은 포트의 개발 서버, 같은 DB)를 쓰는 세션은 순서대로 하나씩 돌린다. 프로젝트마다 무엇이 해당하는지는 프로젝트 규칙([references/projects.md](references/projects.md))에서 찾는다.
- **작은 일은 부모가 직접 한다.** 도구 호출 열 번 안쪽으로 끝나고 한두 파일만 고치는 일(문구, 표시 조건, 순서 등)은 하위 세션을 만들지 않고 부모가 직접 한다. 브랜치·PR 규칙(13절)과 0절 권한은 그대로다. 화면·흐름이 크게 바뀌거나 저장 형식·경제 규칙을 건드리면 작은 일이 아니다. 작은 일을 하거나 "나중에" 칸을 모아 고칠 때 [references/splitting.md](references/splitting.md) "작은 일은 부모가 직접"을 읽는다.

## 2. 브리프 쓰기

**시안 먼저.** 사용자가 보거나 정하는 결과가 있는 일(새 기능, 화면·문구·흐름, 문서 구조·규칙 바꾸기, 여러 PR에 걸친 일)은 맡기기 전에 "지금 ↔ 시안"을 번호 붙여(`A1` …) 보이고, 사용자가 "이대로"라고 할 때까지 고친다. 확정 전에는 시작하지 않고, 확정 시안의 항목을 브리프에 그대로 옮기며, 마무리는 시안 대조 표다. 1절의 작은 일, 바른 결과가 하나뿐인 버그 고침, "시안 없이", 확정된 세부 항목이 있는 일은 빼고, 시안을 만들 때 [references/mockup.md](references/mockup.md)를 읽는다.

하위 세션은 브리프만 보고 일한다. 매번 아래 순서로 쓴다(한국어, 결과부터 쓰는 구어체).

1. **배경**: 프로젝트, 저장소 경로, 브랜치·worktree, 지금 단계(마일스톤, 마지막 태그·커밋).
2. **고정 규칙**: [references/projects.md](references/projects.md)의 순서대로 찾아서 그대로 옮긴다. 그 파일 "공통" 절(명령 꼴, 디자인 스킬 등)도 함께 옮긴다.
3. **할 일**: 체크리스트 번호, 확정 시안 항목(있으면)과 함께. 시안에 없는 것은 더하지 않고 못 하는 항목은 이유와 함께 보고하라고 쓴다. 시나리오(여정)를 먼저 적고 시작하라고 쓴다.
4. **하지 말 일**: 범위 밖 항목, `(사용자)` 표시 줄·사람 테스트(`T1` 등), 번호 바꾸기, 결제.
5. **끝난 모습**:
   - 통과해야 할 확인 명령(범위는 [references/pr-merge.md](references/pr-merge.md) "PR에서 돌릴 테스트"), 체크리스트 ✅ 표시.
   - 커밋·push·PR은 0절 권한 답을 그대로 적는다(예: "커밋은 목적별로, 메시지는 13절 꼴(`feat: …`). 브랜치를 push하고 `gh pr create`로 기본 브랜치 대상 PR을 만들 것. 본문은 13절 꼴. 머지·태그는 하지 말 것"). 쓴 커밋 꼬리표 값도 그대로 적는다.
   - 추가 피드백(부모의 `SendMessage`, PR 리뷰 댓글, CI 실패)은 같은 PR에 커밋을 더해 고치고 본문을 갱신하라고 쓴다.
   - `gh`가 없거나 인증이 안 되면 브랜치 push까지 하고 그 사실을 보고하게 한다. 권한이 없으면 하위 세션은 변경을 커밋하지 않고 남긴 채 보고한다.
6. **기다리는 법**: "백그라운드 작업 알림만 믿지 말고 결과 파일이나 프로세스 종료를 직접 확인할 것."
   외부 서비스를 쓰는 작업이면 "비밀값은 저장소에 넣지 않는다"와 사용자가 준 공개 값(예: 클라이언트 ID)도 넣는다(12절).
7. **보고 형식**: 사용자는 휴대폰 Remote Control로 볼 때가 많다. 마무리 메시지에 PR 링크, 한 일, 커밋, 남은 것, 선택지(번호, 추천은 1번)를 글로 적을 것. 말투는 결과부터 쓰는 구어체로. 커밋 메시지와 PR 제목은 13절 꼴대로 짧고 깔끔하게.

## 3. 시작하기

- `mcp__ccd_session__start_session`. 도구 목록에 이름만 있으면(deferred) 먼저 `ToolSearch`로 `select:mcp__ccd_session__start_session`을 불러온다. 이름만 있는 걸 안 보인다고 여겨 건너뛰지 않는다. 아래 사다리는 정말 못 만들 때만 탄다.
- **새 하위 세션을 만들 수 없으면**(세션 도구가 아예 없거나, 앱이 시작을 막거나) 차례로 ① 쉬고 있는 기존 하위 세션에 `SendMessage`로 맡긴다(마일스톤 일이면 같은 마일스톤 세션만) → ② `Agent`에 `isolation: "worktree"`로 맡긴다 → ③ 부모가 직접 한다. 어느 길이든 한 일 = 브랜치 하나 = PR 하나와 브리프 꼴은 그대로다. 시작 보고 첫 줄에 어느 길로 갔는지 적는다. 자리 비움 중에도 이 사다리를 타고 계속한다. 이때와 하위 세션이 끝난 알림(`<side-sessions-event>`) 턴에서 다음 단계를 시작할 때 [references/start-fallback.md](references/start-fallback.md)를 읽는다.
- context는 `"fresh"`(브리프가 전부 담는다), title은 "개선 2회차 + 이동·리스폰"처럼 무엇을 하는지 바로 보이게.
- 사용자가 맡기라고 했으면 initiation `"user_asked"`.
- 코드를 바꾸는 세션은 `use_worktree: true`로 자기 worktree(브랜치)에서 일하게 한다. 동시에 돌리는 기준과 무거운 프로젝트 예외는 13절. GitHub 원격이 없거나 git이 아닌 프로젝트는 13절 예외를 따른다.
- 모델: 0절에서 정한 테스트·검토 모델과 구현 모델을 쓴다.
- 직전 세션의 보고서나 대화를 통째로 넘기지 않는다. 필요한 사실만 브리프에 요약한다(편향 방지).
- `Agent` 하위 에이전트는 결과를 이번 턴에 바로 받는 일(조사, 나눠 쓰기, 검토 한 번)에만 쓴다. 브랜치·PR로 끝나는 구현 작업은 하위 세션이 먼저고, 하위 세션을 만들 수 없을 때만 위 사다리를 탄다.

## 4. 기다리는 동안

- 폴링하지 않는다. 하위 세션이 턴을 끝내면 앱이 알려 준다.
- 하위 세션이 idle인데 일이 안 끝났으면(예: 오래 걸리는 빌드·테스트 알림을 못 받고 멈춤) `list_events`로 마지막 상태를 보고, 프로세스를 확인한 뒤 `SendMessage`로 "결과 파일을 직접 확인하고 이어서 진행" 하라고 보낸다.
- 하위 세션이 질문하면 0절의 답과 사용자 취향(아래 7절)으로 답할 수 있으면 답한다. 결제나 되돌리기 어려운 공개 결정만 사용자에게 묻는다. 이때도 `AskUserQuestion` UI로 묻는다. 사용자가 자리를 비웠으면(10절) 묻지 않고 "돌아오시면 정할 것"에 모은다.

## 5. 결과 확인 (PR 확인 항목 4개)

부모는 코드를 다시 읽지 않는다(CI가 없을 때 2번의 시험 코드만 예외). 시험도 다시 돌리지 않는다(위험한 PR만 예외). PR 요약과 아래 네 가지를 보고, 위험한 PR이면 검토를 한 번 더 맡긴 뒤(아래 "위험한 PR 검토") 머지할지 정한다. 하위 세션의 보고는 증거가 아니라는 원칙은 2~4번이 맡는다(`gh pr view <번호> --json body,files,mergeable,statusCheckRollup`, `gh pr checks <번호>`).

1. **PR 최종 요약**: 본문이 13절 꼴 네 칸을 다 채웠나("나중에" 칸은 있을 때만).
2. **CI·테스트 통과**: CI가 있으면 PR마다 그대로 기다려 모두 통과(CI 결과만 본다). CI가 없거나 안 돌았으면 부모가 다시 돌리지 않고, 본문 "어떻게 확인했나"의 명령·종료 코드·결과 줄과 그 시험 코드를 읽어 바뀐 동작을 확인하는지 본다. "통과했어요" 한 줄뿐이면 통과로 치지 않고 그 세션에 출력을 달라고 한다. 위험한 PR(아래)만 부모가 그 PR 브랜치에서 한 번 직접 돌린다. 돌린 범위는 [references/pr-merge.md](references/pr-merge.md) "PR에서 돌릴 테스트"에 맞는지 본다. CI가 몇 초 만에 실패하면 시험 실패로 보지 말고 잡이 시작됐는지부터 본다(결제·한도면 아래 "CI 시간").
3. **범위 안**: 바뀐 파일 목록이 브리프 범위 안이고, "하지 말 일"의 파일을 건드리지 않았다.
4. **머지 가능**: 기본 브랜치와 충돌이 없다.

아래 경우에는 [references/pr-merge.md](references/pr-merge.md)의 같은 이름 절을 읽는다.
- **위험한 PR 검토**: 위험한 PR(저장·네트워크처럼 여러 기능이 같이 쓰는 코드 · 형식·스키마·버전 번호 변경 · 인증·결제·비밀값에 닿는 코드 · CI가 없는데 테스트도 새로 쓴 PR)은 검토를 한 번 더 맡긴다. 위험하지 않은 PR은 4개만 본다.
- **검토 지적 나누기**: 지적이 나오면 꼭 고칠 것(동작이 틀림, 데이터가 날아감, 보안, 시험 빠짐)만 같은 PR에서 고치고, 사소한 것(이름, 주석, 꾸밈, 작은 중복)은 "나중에" 칸에 적은 채 머지한다.
- **PR에서 돌릴 테스트**: 관련 테스트만, 전체는 마일스톤 끝에. 브리프에 테스트 범위를 적을 때, 흔들리는 시험이 나왔을 때 읽는다.
- **CI 시간**: CI를 만들거나 고칠 때, 잡이 시작되지 않을 때(한도·결제) 읽는다. 결제는 사용자 몫이고, `--admin`은 사용자가 말하지 않으면 쓰지 않는다.

하나라도 걸리면 그 세션에 `SendMessage`로 같은 PR 안에서 고치게 한다(새 세션을 만들지 않는다). 다 통과해 사용자에게 머지를 물을 때는 13절 "보고 꼴"로 쓴다. 테스트 회차·조사처럼 PR이 없는 세션은 보고서 파일과 확인 명령 결과를 직접 본다.

사용자가 "테스트 > 개선 > 커밋 > 테스트 반복"을 요청하면 [references/qa-loop.md](references/qa-loop.md)를 읽고 따른다.

## 7. 알아서 할 범위

알아서 할 범위가 "결재 빼고 알아서"면(0절 기본값, 사용자가 "매 단계 확인"이라고 했으면 아니다):
- 체크리스트 갱신, 판단 가능한 기획 결정까지 진행한다. 커밋·push·PR·머지·태그는 여기에 들어가지 않는다(0절 권한 답대로만).
- 기획 결정은 비슷한 제품을 조사해 이 프로젝트에 맞는 쪽으로 정하고, 결정 사항을 체크리스트에 기록한다. 단 아래 "사용자 취향인 결정"은 빼고.
- 결제, 계정 생성, 저장소 공개 전환처럼 되돌리기 어려운 일은 하지 않고 사용자에게 남긴다.
- **라이선스·약관은 Claude가 먼저 보고, 사용자에게 확인을 넘기지 않는다.** 외부 자산(모델·폰트·소리·아바타 등), 라이브러리, AI 모델, 외부 서비스를 넣거나 맡기기 전에 [references/decisions.md](references/decisions.md) "라이선스·약관"을 읽는다.

**사용자 취향인 결정은 "알아서"여도 사용자가 정한다.** 제품을 쓰는 사람(게임이면 플레이어)이 보는 것(화면 문구, 보상·답례, 처음 흐름 순서, 이름 붙이기)과 쓰는 외부 서비스를 바꾸는 것이다. 내부 구조·코드·데이터 형식은 Claude가 정한다. 시안(2절)이 있으면 시안 항목으로 넣어 확정받고, 시안 뒤에 새로 생긴 것만 선택 UI로 묻는다. 이런 결정이 생기면 [references/decisions.md](references/decisions.md) "사용자 취향인 결정"을 읽는다(묻는 꼴, 자리를 비웠을 때).

## 8. 보고

짧게, 휴대폰에서 읽기 좋게 쓴다. 세션은 `[제목](#local_…)` 링크로 적는다.

- 끝난 것: 세션, PR 링크(머지했는지), 태그, 체크리스트 번호
- 확인한 것 / 확인 못 한 것
- 다음 작업: 번호 붙은 선택지, 추천은 1번

**"진행중이니?", "남은 거?", "얼마나 걸려?"에는 늘 같은 꼴(지금 · 끝난 것 · 남은 것 표 · 미룰 후보 · 정하실 것)로 답한다.** 이런 물음이 오면 [references/progress.md](references/progress.md) "진행 물음 꼴"을 읽는다. 숫자는 직접 보고 적고, 예상 시간을 모르면 지어내지 않는다.

**큰 단계 알림은 기본이 끔이다.** "내 방식"에 켬으로 적혀 있을 때만 [references/progress.md](references/progress.md) "큰 단계 알림"을 읽고 따른다.

## 9. 기획에서 이어질 때

한 주제 기획(rules.md "기획 크기")에서 온 세부 항목은 체크리스트 번호가 그 주제 절(예: `P28-02`) 아래에 있다. 마일스톤 세부 항목(한 줄 = 한 작업 단위)을 맡길 때는 그 줄의 체크리스트 번호와 "끝났다고 보는 것"을 브리프의 할 일·끝난 모습에 그대로 옮긴다(이것이 시안 구실을 하고, 화면·문구가 걸린 줄만 2절 시안을 먼저 거친다). 마일스톤이 끝나면 `roadmap` 스킬의 갱신 플로우(시나리오 🔜 → ✅, 점수 다시 계산)를 부른다. 이 스킬은 `roadmap`의 개발 플로우에서도 불린다.

## 10. 자리 비움

사용자가 "병원 다녀올게", "자러 갈게", "다되면 마무리해줘"처럼 자리를 비우면 [references/wrap-up.md](references/wrap-up.md) "자리 비움"을 따른다: 떠나기 전에 시안을 확정받고(확정 못 받은 일은 시작하지 않음), 그 뒤로는 선택 UI로 묻지 않고, 되돌릴 수 있는 것은 추천대로 정해 적고, 되돌리기 어려운 것은 "돌아오시면 정할 것"에 모은다. 맡은 일이 끝나면 마무리하고 멈춘다.

## 11. 마무리

"다되면 문서 정리하고 마무리해줘"라고 했거나, 자리 비움 중 일이 다 끝났거나, 마일스톤이 끝났으면 [references/wrap-up.md](references/wrap-up.md) "마무리"를 한다: PR 상태 확인 → 머지(0절 권한대로) → 전체 테스트(마일스톤 끝) → 시안 대조 표 → 문서 정리(바뀐 것만) → 이어 하기 메모 → 돌아오셨을 때 보고. 다른 PC 준비, 정리 후보 보이기, 부모 세션 넘기기, 메모리 정리는 사용자가 말할 때만 한다.

## 12. 외부 준비와 비밀값

로그인·클라우드 저장·결제·지도처럼 외부 서비스가 필요하면 [references/external-setup.md](references/external-setup.md)를 따른다: Claude는 계정을 만들거나 콘솔에 값을 넣지 않는다. 사용자가 콘솔에서 할 일은 단계·넣을 값·비용을 먼저 알려 주고, 그동안 외부 값이 필요 없는 부분을 브랜치에서 진행한다. 비밀값은 어떤 저장소에도 넣지 않는다.

## 13. PR과 머지

자세한 규칙은 [references/pr-merge.md](references/pr-merge.md)에 있다. PR 본문·커밋 메시지를 쓰거나, 머지·정리·예외를 정할 때 그 파일을 읽는다. 브리프에 PR 본문 꼴과 커밋 메시지 꼴을 옮길 때도 거기서 옮긴다.

- 한 작업 = 브랜치 하나 = PR 하나. 추가 피드백은 같은 PR에 커밋을 더한다.
- 같은 파일을 건드리는 일은 동시에 돌리지 않는다(개수 제한은 프로젝트 규칙대로). 무거운 프로젝트는 기본 사본에서 하나씩.
- PR 본문 = 최종 요약(네 칸: 무엇을 바꿨나 · 어떻게 확인했나 · 범위 밖에서 건드린 것 · 확인 못 한 것·남은 것, 사소한 지적이 있으면 "나중에" 칸).
- 커밋 제목 = `<타입>: <결과 한 줄>`, 한 커밋 = 목적 하나.
- 머지는 부모가 5절 확인 뒤 0절 권한대로, Squash and merge로. 태그는 사용자가 요청할 때만.
- 머지를 물을 때는 "보고 꼴"로, 머지 뒤 하위 세션은 묻지 않고 기본으로 보관한다("내 방식"에서 바꾼다).
- 예외: GitHub 원격 없음, main push가 곧 배포, 한 번에 하나만 도는 도구, 서로 기대는 작업.
