# 프로젝트별 고정 규칙 찾기

브리프의 "고정 규칙"은 프로젝트마다 다르다. 아래 순서로 찾는다.

1. **`projects.local.md`** (같은 폴더, 이 PC에만 있는 파일): 있으면 해당 프로젝트 부분을 그대로 옮긴다. 개인 저장소 이름, 커밋 작성자, 내부 경로처럼 공개하면 안 되는 규칙은 이 파일에만 둔다. git에는 올리지 않는다(`.gitignore`).
2. **저장소의 `CLAUDE.md`, `README`, 기여 안내**
3. **메모리**: 1·2와 다르면 메모리가 우선이다(최근 결정이 반영돼 있다). 그때 `projects.local.md`도 고친다.

찾은 규칙이 없는 프로젝트는 아래 항목을 채워 `projects.local.md`에 새 부분으로 추가한다. 파일이 없으면 만든다.

## 템플릿

```markdown
## <프로젝트 이름>

- 경로, 원격 저장소, 기본 브랜치, 공개 여부
- push가 곧 배포인지 (그렇다면 테스트 통과 후에만 push)
- 커밋 규칙: 메시지 언어·형식, 작성자, 붙여야 할 줄
- 태그 규칙: 이름 형식, 누가 언제 다는지
- 테스트 명령: PR마다 돌릴 것(단위 전체·기능별·배포·빌드 검사), 마일스톤 끝 전체 검증용
- 한 번에 하나만 돌 수 있는 도구 (예: 게임 엔진 배치 실행, 같은 포트의 개발 서버)
- 개발·테스트 공간 (worktree, 미리보기 포트)
- 건드리면 안 되는 것 (사용자 항목, 실제 사용자 데이터 폴더, 잠긴 기획 규칙)
- 쓰면 안 되는 말 (예: 다른 제품 이름)
- 진행 기록·QA 보고서 위치
```

## 공통 (어느 프로젝트나)

`roadmap` 스킬의 공통 규칙(rules.md)도 번호와 한국어 파일은 여기를 따른다.

- 체크리스트는 `P06-01-00` 같은 계층 번호, ✅ 확정 / ⬜ 열림 / ⏸ 보류, 바뀐 것 🔄, 새것 🆕로 쓴다. **번호는 바꾸지 않는다.** 합쳐지거나 빠지면 "(통합됨 → X)", "(삭제)"로 표시한다.
- 확인이 필요하거나 구현이 어려운 항목은 후순위로 미룬다.
- 한국어가 든 파일을 고칠 때는 인라인 셸 명령(`node -e`, heredoc) 대신 스크립트 파일이나 파일 쓰기·고치기 도구를 쓴다. 따옴표와 한글이 깨지기 쉽다.
- **확인 창이 안 뜨는 명령 꼴.** 허락 목록(`settings.json`의 `Bash(git *)` 같은 머리)에 맞아야 묻지 않고 돈다. 부모도 하위 세션도 이렇게 쓴다.
  - git·gh와 빌드 도구는 Bash 도구로 부른다. 같은 명령을 PowerShell 도구로 부르지 않는다.
  - 한 줄에 명령 하나만 쓴다. `cd … &&`, 파이프, `;`, 앞에 붙인 변수(`X=… cmd`)를 쓰지 않는다. 폴더는 `git -C <경로>`처럼 명령의 경로 옵션으로 가리킨다(예: cargo는 `--manifest-path`).
  - 커밋 메시지, PR 본문, 머지 본문은 `$(cat <<EOF …)` 대신 파일 쓰기 도구로 스크래치 파일에 쓰고 `git commit -F <파일>`, `gh pr create --body-file <파일>`로 넣는다.
- **디자인이 필요한 일**(화면, 아이콘, 소개 페이지 같은 보이는 것)은 Claude의 디자인 스킬을 쓴다. 쓸 수 있는 디자인 스킬이 없으면 보고에 적는다.
