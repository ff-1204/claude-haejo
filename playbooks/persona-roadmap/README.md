# 페르소나에서 마일스톤까지, 그리고 개발 반복

제품(게임, 앱, 도구)을 **누가 무엇을 하려는지**에서 출발해 순서 있는 마일스톤으로 만들고, 그 마일스톤을 하위 세션으로 구현·검토·테스트하는 과정이다. 어느 프로젝트에서나 쓸 수 있게 일반화했다.

```
0 핵심 경험·범위 → 1 페르소나 → 2 시나리오 → 3 체크리스트 → 4 매핑
→ 5 비중 점수 → 6 우선순위 → 7 마일스톤 → 8 세부 항목
→ 9 개발 반복(맡기기 → 검토 → 테스트) → 10 시나리오 갱신 → (5로 돌아감)
```

이 과정은 스킬로 돌린다. 상위 스킬 [`roadmap`](../../skills/roadmap/)에게 "처음부터 기획해줘", "페르소나 하나 더 추가해줘", "M2 끝났어, 시나리오 갱신해줘"처럼 말하면 하위 스킬 일곱 개를 순서대로 부른다. 이 문서는 사람이 읽는 개요이고, 템플릿과 점수 스크립트는 각 하위 스킬 폴더에 있다.

## 진행 원칙

- **정할 수 있는 건 Claude가 정하고, 어려운 결정만 사용자에게 묻는다.** 물을 때는 선택 UI로 한 번에 묻고, 추천을 첫 번째에 둔다. 단계마다 "사용자에게 물을 것"을 적어 두었다.
- **문서마다 날짜와 근거를 맨 위에 적는다.** 예: "2026-10-22. 근거: 핵심 경험 ①~⑤, 범위 결정."
- **번호는 바꾸지 않는다.** 빠지면 "(삭제)", 합쳐지면 "(통합됨 → X)"로 표시한다.
- 문서는 저장소 안에 둔다. 각 단계가 끝날 때 커밋할지는 프로젝트 규칙을 따른다.

## 0. 핵심 경험과 범위

| | |
|---|---|
| 만드는 것 | 핵심 경험 3~6개(번호 ①②③…), 범위(대상 기기, 온라인 여부, 뺄 것) |
| 규칙 | 핵심 경험은 "사용자가 하는 일" 문장으로 쓴다(예: "친구가 만든 것을 받아 고쳐 쓴다"). 기능 이름이 아니다. |
| 사용자에게 물을 것 | 핵심 경험 목록 확정, 범위에서 뺄 것 |

이후 모든 문서는 이 번호와 범위를 기준으로 쓴다. 핵심 경험이 바뀌면 1부터 다시 본다.

## 1. 페르소나 — `roadmap-personas`

- 기본 5명으로 시작한다(핵심 경험마다 1명 이상, 한 사람이 여러 특성을 겸해도 됨). 필요하면 "페르소나 하나 더 추가해줘"로 늘린다. 이미 있던 페르소나는 앞 번호로 그대로 둔다.
- 핵심 경험별로 묶는다(A. ①을 주로 하는 사람 …). 나이·상황·능력이 고르게 퍼지게 한다: 처음 해 보는 사람, 오래 한 사람, 어린 사람, 나이 든 사람, 접근성이 필요한 사람, 여럿이 쓰는 사람, 혼자 쓰는 사람, 만드는 사람, 쓰기만 하는 사람.
- 한 명당 다섯 줄로 쓴다.
  1. 번호 이름 — 나이, 한 줄 소개
  2. **상황**: 기기, 쓰는 시간, 비슷한 제품 경험
  3. **즐기는 것**: 핵심 경험 번호와 하고 싶은 일
  4. **한마디**: 그 사람이 할 법한 말
  5. **막힐 곳 → 필요한 것**: 체크리스트 번호(없으면 3단계에서 만든다)
- 사용자가 페르소나를 추천하면 다음 번호로 더하고 7절의 "추가할 때"를 따른다.

## 2. 시나리오 — `roadmap-scenarios`

- 페르소나마다 **"하루 한 장면"**을 5~8단계로 쓴다. 그 사람이 실제로 할 순서대로 쓴다.
- 단계마다 지금 되는지 표시한다.
  - ✅ 지금 됨
  - 🔜 계획됨 (체크리스트 번호)
  - ❌ 계획에 없음 → 맨 아래 "새 후보"에 모은다
- 나중에 테스트 재료가 된다: 자동 여정 테스트, 사람이 해 보는 확인 목록, QA 회차의 케이스.

## 3. 체크리스트에 적기 — `roadmap-map`

- 페르소나의 "필요한 것"과 시나리오의 ❌를 체크리스트 항목으로 만든다.
- 체크리스트는 두 겹이 좋다: **기획**(무엇을, 왜) / **구현**(어떻게, 확인 방법). 작은 프로젝트는 하나로 합쳐도 된다.
- 번호는 `F01-02-03`처럼 계층으로, 상태는 ✅ 확정·끝 / ⬜ 열림 / ⏸ 보류, 바뀐 것 🔄, 새것 🆕.

## 4. 매핑 — `roadmap-map`

- 시나리오의 **모든 단계**를 체크리스트 번호에 잇는다. 번호가 없는 단계에는 `→ [번호]`를 붙인다.
- 잇다가 없는 기능이 나오면 체크리스트에 새 항목을 만든다. 끝나면 "빈 단계 0"이어야 한다.
- 매핑 문서 맨 위에 단계 수, 새로 만든 항목, 빈 단계 수를 적는다.

## 5. 비중 점수

```
점수 = 그 기능 묶음이 필요한 사람 수 × 2 + 그 묶음이 나온 시나리오 단계 수
```

- 사람 수를 두 배로 치는 이유: 한 사람이 여러 번 부딪히는 것보다 여러 사람이 부딪히는 것이 더 크다.
- 묶음 단위(번호 앞 두 마디, 예: `F01-02`)로 센다.
- 등급을 나눈다. 기본값은 1등급 ≥ 15, 2등급 ≥ 9, 3등급 ≥ 5, 4등급 나머지. 페르소나 수가 크게 다르면 조정한다.
- 아직 안 된 것(🔜)과 이미 된 것(✅)을 따로 표로 만든다. ✅ 표는 "이미 된 기능이 몇 명을 받치는지"를 보여 줘서, 손대면 안 되는 바탕 기능이 보인다.
- 계산은 `roadmap-score`가 [score.js](../../skills/roadmap-score/scripts/score.js)로 한다. 옵션은 그 스킬에 있다.

## 6. 우선순위

1. 점수 순서대로 늘어놓는다.
2. 세 가지만 고친다.
   - 다른 작업의 검증을 받치는 **바탕 일**(오류 보고, 자동 테스트)은 맨 앞
   - 다른 기능이 **기대는 것은 먼저**
   - **같은 코드를 쓰는 것은 묶음**
3. 뒤로 미루는 규칙 두 가지를 적용한다.
   - **구현이 어려운 것은 뒤로.** 난이도: 쉬움(하루 안팎) / 보통(며칠, 새 화면 하나) / 어려움(한 주 이상, 새 큰 편집기, 네이티브 빌드, 새 네트워크 흐름, 기존 원칙과 따로 맞춰야 하는 것). 한 묶음 안에 쉬운 부분과 어려운 부분이 섞이면 쪼갠다.
   - **사람 확인이 필요한 것은 더 뒤로.** 사람의 눈·손·장비가 있어야 끝나는 것(맛 고르기, 실제 장비, 여러 기기, 다른 프로그램에서 열어 보기).
4. 최종 순서: 쉬움·보통(점수순) → 어려움(점수순) → 확인 필요 → 사람 손 확인 몰아서. 보류는 따로.
5. 순서는 구현 체크리스트 맨 앞 한 항목(예: `I00-00`)에 한 줄로 적는다. 왜 그 자리인지 짧게 붙인다.

사용자에게 물을 것: 미루는 규칙을 쓸지, 난이도 기준이 맞는지(기본값을 추천으로).

## 7. 마일스톤 — `roadmap-milestones`

- 6의 순서를 잘라 마일스톤 4~8개로 나눈다. **날짜 없이 순서만.**
- 이름은 **사용자 경험 문장**으로 짓는다(예: "첫날이 즐겁다", "놀러 오세요", "누구나 편하게").
- **끝났다고 보는 기준 = 정해 둔 페르소나 몇 명의 시나리오 🔜 단계가 모두 ✅**(사람 확인 단계 빼고).
- 크기(쉬움·보통·어려움 개수)와 태그 이름(`v0.N.0-<짧은-영어>`)을 적는다.
- 사람이 하는 테스트(지인 테스트, 실제 장비 점검)는 마일스톤 사이에 끼운다. 그 결과로 나온 문제는 다음 마일스톤 앞에 넣는다.
- "지금 있는 곳", "그다음(범위 밖)", "정한 것"을 함께 적는다.

사용자에게 물을 것: 마일스톤 수와 경계, 사람 테스트를 끼울 자리, 태그를 달지.

### 페르소나를 추가할 때

시나리오 추가 → 매핑 → 점수 다시 계산 → **순서가 바뀐 곳만** 고친다. 무엇이 왜 바뀌었는지는 매핑 문서 끝에 절을 하나 더해 기록한다.

## 8. 세부 항목

- 마일스톤마다 표로 쓴다: **번호(M1-1) / 무엇 / 체크리스트 번호 / 끝났다고 보는 것**.
- **한 줄 = 한 작업 단위**: 구현 → 다른 에이전트 검토 → 반영 → 검증을 한 번 도는 크기.
- "끝났다고 보는 것"은 확인할 수 있는 문장으로 쓴다(자동 테스트, 측정값, 화면).
- 끝나면 `M1-1 ✅ (날짜)`로 표시하고, 뒤로 넘긴 것은 번호와 함께 따로 적는다.

## 9. 개발 반복

`roadmap-teammate` 스킬([../../skills/roadmap-teammate/](../../skills/roadmap-teammate/))로 진행한다.

1. **시작 전 질문**: 모델, 알아서 할 범위, 시간을 선택 UI로 한 번에 묻는다.
2. **세부 항목 하나 = 하위 세션 하나.** 브리프에 체크리스트 번호와 "끝났다고 보는 것"을 그대로 옮긴다.
3. **구현 → 검토**: 구현한 세션이 아닌 새 에이전트가 읽기만 하며 검토한다(꼭 고칠 것 / 고치면 좋은 것). 고치고, 그 항목의 시나리오 여정 하나로 중간 확인을 하고, 끝에 전체 검증을 한 번 한다.
4. **마일스톤이 끝나면 테스트 반복(QA 루프)**: 매 회차 새 세션이 시나리오를 케이스로 삼아 테스터처럼 확인한다. 개선 세션이 고치고, 목적별로 커밋한다.
5. 기획 결정이 필요한 것이 나오면 비슷한 제품을 조사해 이 프로젝트에 맞는 쪽으로 정하고 체크리스트에 기록한다. 결제나 되돌리기 어려운 일만 사용자에게 남긴다.

## 10. 시나리오 갱신과 다시 보기

- 마일스톤이 끝나면 시나리오의 🔜를 ✅로 바꾸고 단계 끝에 "M1 날짜"를 붙인다.
- 테스트에서 나온 새 문제는 체크리스트에 🆕로 적고 매핑한다.
- 그다음 5로 돌아가 점수를 다시 계산하고, 순서가 바뀐 곳만 로드맵에 반영한다.
