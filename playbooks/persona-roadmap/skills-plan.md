# 기획 플로우 스킬화 계획 (상위 스킬 1 + 하위 스킬 7)

> 2026-10-24. 근거: [README.md](README.md)의 0~10단계. 사용자가 "~~ 해줘"라고 말하면 **상위 스킬**이 플로우를 고르고, 단계마다 **하위 스킬**을 순서대로 부른다. 하위 스킬은 혼자서도 부를 수 있다.
> 상태: ✅ 정함 · ⬜ 열림 · ⏸ 보류. 번호는 바꾸지 않는다.

## S01 구조

```
roadmap (상위: 말 → 플로우 고르기 → 하위 스킬 순서대로 → 확인 지점에서 묻기 → 보고)
 ├─ roadmap-core        0  핵심 경험·범위
 ├─ roadmap-personas    1  페르소나 (새로 / 더하기)
 ├─ roadmap-scenarios   2  시나리오 (새로 / 더하기 / 갱신)
 ├─ roadmap-map         3·4 체크리스트에 적기 + 매핑
 ├─ roadmap-score       5  비중 점수 (score.js)
 ├─ roadmap-priority    6  우선순위 + 미루기 규칙
 ├─ roadmap-milestones  7·8 마일스톤 + 세부 항목
 └─ roadmap-teammate       9  개발 반복 (이미 있음, 재사용)
```

- ✅ S01-01 이름 앞머리는 `roadmap-`로 통일한다. `/roadmap-score`처럼 혼자 부를 때 무엇인지 바로 보이게 하기 위해서다.
- ✅ S01-02 10단계(시나리오 갱신)는 새 스킬을 만들지 않고 `roadmap-scenarios`의 "갱신" 모드로 둔다. 입력과 출력이 같은 파일이라서다.
- ✅ S01-03 3단계(적기)와 4단계(매핑)는 하나로 합친다. 매핑하다가 없는 항목을 적으므로 따로 돌면 왕복이 생긴다.
- ✅ S01-04 9단계는 `roadmap-teammate`를 그대로 쓴다. 상위 스킬은 세부 항목 표를 브리프 재료로 넘기기만 한다.
- ✅ S01-05 기획 단계(0~8)는 **이 세션 안에서** 한다. 앞 단계 결과가 바로 다음 입력이라 하위 세션으로 나누면 오히려 느리다. 예외: 시나리오를 30명 넘게 쓸 때는 페르소나 묶음별로 서브에이전트를 나눠 쓰고, 상위가 합친다.

## S03 하위 스킬 계약

모든 하위 스킬은 같은 꼴을 따른다: **입력 문서 → 하는 일 → 출력 문서 → 한 줄 보고.** 상위가 없을 때 혼자 불려도 입력 문서를 스스로 찾고, 없으면 무엇이 필요한지 말하고 멈춘다.

| # | 스킬 | 입력 | 출력 | 모드 | 혼자 부를 때 |
|---|---|---|---|---|---|
| ✅ S03-01 | `roadmap-core` | 콘셉트 문서, README, 사용자 말 | 핵심 경험 ①~⑥ + 범위 (콘셉트 문서나 `personas.md` 머리) | 새로 / 바꾸기 | `/roadmap-core` (S07-03) |
| ✅ S03-02 | `roadmap-personas` | 핵심 경험, 범위 | `personas.md` | 새로 / 더하기 | `/roadmap-personas` (S07-03) |
| ✅ S03-03 | `roadmap-scenarios` | `personas.md`, 체크리스트 | `persona-scenarios.md` | 새로 / 더하기 / 갱신 | `/roadmap-scenarios` (S07-03) |
| ✅ S03-04 | `roadmap-map` | 시나리오, 체크리스트 | 체크리스트 🆕 항목, `persona-checklist-map.md` 머리(빈 단계 0) | 전체 / 더해진 것만 | `/roadmap-map` (S07-03) |
| ✅ S03-05 | `roadmap-score` | 시나리오 | 매핑 문서 1·2절 (🔜 표, ✅ 표) | — | `/roadmap-score` (S07-03) |
| ✅ S03-06 | `roadmap-priority` | 점수 표, 체크리스트 | 매핑 문서 3~5절, 구현 체크리스트 `I00-00` 순서 | 새로 / 바뀐 곳만 | `/roadmap-priority` (S07-03) |
| ✅ S03-07 | `roadmap-milestones` | `I00-00` 순서, 시나리오 | `roadmap.md` (마일스톤 표 + 세부 항목) | 새로 / 바뀐 곳만 / 끝 표시 | `/roadmap-milestones` (S07-03) |

각 스킬에 함께 두는 것:

- ✅ S03-08 템플릿은 그 단계를 맡은 스킬 폴더의 `assets/`로 옮긴다(personas → `roadmap-personas/assets/personas.md` 등). 한 곳에만 둔다.
- ✅ S03-09 `score.js`는 `roadmap-score/scripts/`로 옮긴다. `roadmap-priority`는 점수를 직접 세지 않고 이 스크립트 결과만 쓴다.
- ✅ S03-10 공통 규칙(번호 안 바꿈, ✅⬜⏸🔄🆕, 날짜·근거 머리, 한국어 파일은 스크립트 파일이나 쓰기 도구로)은 상위 `roadmap/references/rules.md` 한 곳에 두고, 하위 스킬은 그 파일을 읽으라고만 쓴다.
- 🔄 S03-11 "더해진 것만"·"바뀐 곳만"·"끝 표시" 모드는 매핑 문서 "6. 바뀐 기록"의 그날 절에 한 줄을 더한다(rules.md "바뀐 기록", S07-08).

## S08 2회차 확인 결과와 고친 것 (2026-10-24)

> 새 테스트 세션(Opus)이 새 가상 프로젝트(동네 헬스장 PT·수업 예약 앱, 페르소나 6 → 7명)를 처음부터 돌렸다. S07-01~14 중 13개 해결, S07-04는 일부 해결. 꼭 고칠 것 1 · 고치면 좋은 것 9. 아래는 부모 세션이 고친 것. 이 고침은 3회차 테스트를 하지 않았다(score.js만 사례 파일로 확인).

- ✅ S08-01 **단계 문장이 뒤 마일스톤 기능에 기대면 끝 기준을 이룰 수 없고 갱신이 거짓 ✅를 만듦** (꼭 고칠 것)
  - map 2: 단계가 쓰는 기능 번호를 **모두** 단다(앞 상태 포함).
  - priority 2: 기댐을 시나리오 단계의 여러 번호로도 본다.
  - milestones 3: 고른 단계마다 문장을 읽어 뒤 마일스톤 번호가 있으면 기준에서 빼고 이유를 적는다. 섞인 단계는 이 마일스톤 조각만.
  - scenarios 갱신 3: 번호가 끝나도 문장 전체가 되는지 보고, 안 되면 일부만 꼴로 남긴다.
- ✅ S08-02 섞인 번호 단계의 끝 기준: milestones 3에 한 줄.
- ✅ S08-03 쪼갠 조각과 시나리오 번호 어긋남: priority가 쪼갤 때 시나리오 번호도 조각으로 바꾸고, scenarios 갱신이 아래 조각 번호도 잡는다.
- ✅ S08-04 매핑 문서 안 낡음 판단: 1절 아래 `> 점수:`, 3절 아래 `> 순서:` 시각. 머리 `> 갱신:`은 map 몫.
- ✅ S08-05 혼자 불릴 때 줄: 각 하위 스킬 "한 줄 보고" 끝에 직접 적음, 고친 것이 없으면 "바뀐 것 없음".
- ✅ S08-06 페르소나가 적을 때 순서 흔들림: priority 바뀐 곳만에 "점수 차 3 이하나 사슬 통째 이동이면 자리 그대로 + 기록". score 등급 하한을 페르소나 수에 맞춰 안내.
- ✅ S08-07 원래 있던 사람이 없을 때: 템플릿 줄을 "원래 있던 사람: <01~0X | 없음>. <NN~MM은 사용자 추천.>"으로.
- ✅ S08-08 ❌ → 🔜 꼴 하나로: `🔜 (번호) ← 새 후보 N`.
- ✅ S08-09 score.js: 여러 조각 줄에서 표시 없는 조각은 따라가지 않고 "표시 없는 단계"로 알림(그 조각 번호는 세지 않음). 문장 안 ` / `는 해가 없음 확인.

## S10 실사용에서 나온 개선 네 가지 (2026-10-28)

> 근거: 도리의 정원 세션(10-25~28)이 roadmap으로 P28 "두 속도"를 기획하고 roadmap-teammate로 M1~M2를 하위 세션 13개 넘게 나눠 개발한 기록. 사용자가 고른 네 가지를 넣고, 새 테스트 세션(Opus)이 기존 테스트 프로젝트 사본에서 "한 주제" 기획을 돌리고 teammate 규칙을 상황 네 개로 따져 봤다(3회차). 꼭 고칠 것 6 · 고치면 좋은 것 15를 반영. 반영 뒤 다시 돌려 보지는 않았다(score.js만 사례로 확인).

- ✅ S10-01 **한 주제 기획**: 시작 질문에 "기획 크기: 전체 / 한 주제". 한 주제면 주제 폴더(`docs/기획/<절>-<이름>/`), 기존 체크리스트의 다음 절(P28), 순서 줄과 바탕 일은 절 번호로(`P28-00`, `P28-00-01`, 3회차 G1: `I00-00`이 둘이 되던 것), 페르소나는 주제 유형별·제품 다음 번호부터, 태그는 기존 순서를 이어 씀.
- ✅ S10-02 **자리 비움·마무리**(roadmap-teammate 10·11절, `references/wrap-up.md`): 자리 비움이면 묻지 않고 "추천대로 정한 것"·"돌아오시면 정할 것"으로 나눔, 깨어 있기. 마무리 = 전체 확인 → 배포·태그(덜 끝난 마일스톤은 태그 안 함) → 문서 정리 → 메모리 → 이어 하기 메모. 다른 PC면 배포 아닌 브랜치에 push(3회차 G3).
- ✅ S10-03 **작은 고침 묶기**(teammate 1절): "빠른 고침" 세션 하나에 이어 붙이고, 배포는 부모가 확인한 뒤 묶어서 한 번. 1절 첫 점과 부딪히던 것 정리(3회차 G4).
- ✅ S10-04 **외부 준비·비밀값·공개 저장소**(teammate 12절, `references/external-setup.md`, rules.md "공개 저장소"): 콘솔 안내서를 먼저, 코드는 브랜치에서. 비밀값은 어떤 저장소에도 안 넣음, 이미 붙여 넣었으면 재설정 안내, 키 검사 목록(3회차 G6). 공개 여부 알아내는 법.
- ✅ S10-05 **score.js**: `--prefix`로 걸러져서 빈 단계를 "번호 없는 단계"가 아니라 "다른 절만 가진 단계"로 따로 셈(3회차 G2). 한 주제면 점수를 두 번(새 절만 / 옵션 없이) 내고, 기존 절 🔜 항목은 "기대는 기존 항목"으로.
- ✅ S10-06 **기획이 여럿일 때**(3회차 G5): 상태 보기는 기획마다, 개발 플로우는 사용자가 고른 기획 또는 가장 최근 기획.
- ✅ S10-07 그 밖(3회차 N): 한 주제 마일스톤 2~4개, 다른 기획에 기대는 마일스톤 표시, 태그 번호를 다른 로드맵의 "태그 전"까지 보고 정함, core "주제" 모드, 예전 꼴 매핑 문서의 낡음 판단, 처음 말에 "알아서 끝까지"면 시작 질문도 추천대로, 빠른 고침 세션의 0절·겹침·보관, teammate 설명 낱말(구글 문서 편집과 구분).
